# Warlock invariants

The authoritative record of this repository's hard invariants and the reasoning behind them, moved out of `CLAUDE.md` on 2026-08-10 so that every session loads a short index instead of this file. Nothing was cut in the move. The maintenance rule is unchanged: when an invariant changes, this file is updated the way `CLAUDE.md` used to be — `CLAUDE.md` itself stays a pointer. Read the section covering a subsystem before modifying it.

## What this is

Local AI 3D asset generator: text or image prompt → SDXL-Turbo (reference PNG) → `trellis-server.exe` (vendored native binary, not the Python TRELLIS package) → textured GLB, in a single-process desktop app: a pygame window, one ModernGL context, imgui panels drawn through it. No HTTP, no browser.

## Hard invariants

**Three threads, and the split is the design.** The pygame frame loop reads `JobStore` directly (one connection behind an RLock, so that is safe) and must never block; the `warlock-loop` thread hosts the asyncio loop the `Worker` lives on, because `wake` is loop-affine and cancellation is a coroutine; a four-thread `TaskRunner` runs everything that blocks -- exports, Blender bakes, prune, the tokenizer. `studio/runtime.py` is the old FastAPI lifespan, port for port. Progress needs no protocol at all: the frame loop calls `worker.progress.snapshot()` directly, and `TaskRunner` grew the same thing for tasks — a dict under the *same* lock as `_pending` (an answer assembled from two locks can say "not busy, 40%"), returning `{"percent", "label"}` so a pane draws a queue job and a task the same way. It is `set_progress`, not `Done`, because `Done` arrives only at completion: enough for a two-second export, not for a 16 GB download. A report for a key that is not in flight is dropped, or a child's last line landing after collection resurrects a bar nothing will clear.

**What "must never block" costs, concretely.** Four things measured as real stalls, all fixed the same way — do less per frame, not on another thread, because GL is the one context. `attach_files` takes a caller-owned cache stamped `(status, job-dir mtime)`, which is sound because every `LISTED` name is answered by *existence* and a file appearing or going moves the directory's mtime: one stat per row instead of ten, on a page of two hundred, twice a second, unbounded after "load more". **That mtime has a resolution, though, and it is coarse enough to matter**: adding a file left the directory's mtime unchanged 155 times in 200 on this machine (`docs/measurements/2026-08-07-directory-mtime-granularity.md` — Windows writes it from the system clock, whose tick is 15.6 ms unless something has asked for better), so a write landing after a listing but inside the stamped mtime's own tick is invisible to the stamp *permanently*, every later comparison matching a stale answer — which is exactly the case the mtime half exists for, a rig written into the **source** job's directory while that job stays `done`. So `MTIME_RACE_NS` applies git's racily-clean rule: a stamp is stored only once its mtime is safely in the past, and a directory touched moments ago is answered correctly and simply not remembered. The clock is read **after** the listing and that ordering is the proof, not a detail — the hazard needs a write later than the listing yet still in the mtime's tick, which cannot exist if the listing already finished a tick after the mtime. `_sync_viewer` submits `Viewer.parse_model` (pure CPU: accessor decode plus a PNG per texture slot) and adopts the result in `_adopt_model` on the frame thread, where `GpuModel` must stay — the parse used to run inline on the frame a job transitioned to done, which is when the file is largest and coldest. `viewer.pending` is what stops the timer redispatching and what makes a result the selection has moved past droppable; `load_model` survives for the callers where the wait *is* the response (entering the pose editor, loading a Review unit), because a hand-over there flashes an empty viewport instead. **`adopt_model` and `clear` clear `pending` themselves**, or the blocking path leaves it naming a parse dispatched a moment earlier which still matches when it lands and is adopted over the top — in the pose case discarding the editor and its unsaved rotations, bypassing the confirm `pose_panel.guard` puts in front of every other exit. And `viewer/sheet.StripRender` renders **one cell per `step()`**: each cell is a draw plus a synchronous `read_rgba`, and sixteen of those in one frame is a visible freeze. The marching ants are the fourth and the same lesson: `studio/ants.py` prepares a selection's loops once (closed vertex array plus cumulative arc length, cached on mask identity beside the contour trace, because both are pure functions of the mask), and the frame does whole-array numpy plus one `add_line` per straight **run** — not one per unit lattice step per dash, which on a 2048² lasso was 27 844 Python iterations *per frame, forever*. Two things about that are deliberate. The dash pattern is a function of arc length from the loop's start, so it is continuous across vertices rather than restarting at each one. And **a dash is split at every vertex it crosses**, with only exactly-collinear pieces merged back: the tempting version interpolates a dash's two endpoints and draws the chord between them — one line per dash instead of per lattice step, which is the whole speed argument — and it is wrong, because a contour is a staircase and a chord across six steps of one straightens it out and skips a one-pixel spike entirely. The merge is where the speed actually comes from and it is exact: a marquee edge is one line per dash, and a staircase, which genuinely turns every pixel, costs what it always did.

**The service layer is the only business logic.** `service/` holds what `app.py`'s route bodies used to, as plain synchronous functions taking a `WarlockService` first and raising `service.errors` exceptions. The panes call it, the tests call it, and nothing else exists between the UI and the queue. `service/jobs.py` is a **facade** since 2026-08-11: the implementations live in `service/_jobs_{create,list,lifecycle,resubmit,rework}.py` and are re-exported from it unchanged, because every caller imports the module and calls by attribute, and several tests monkeypatch names on it (`create_job`, `import_mesh`, `list_jobs`, `storage_sizes`, `MAX_LIST_LIMIT` — the last read back through the facade at call time by the two functions that consult it).

**Single sqlite3 connection, serialized by an explicit lock.** `JobStore` (`db.py`) wraps one `sqlite3` connection opened with `check_same_thread=False`, and every method that touches it takes `self._lock` (an `RLock`) first. `asyncio.to_thread` does *not* serialize anything — its default executor is a multi-worker pool, so concurrent requests genuinely land on different threads — which makes that lock the only thing keeping two `commit()`s apart. Any new method that reaches `self._conn` must take the lock too. `progress.py` is separately in-memory-only and never touches the DB from its own reader thread; keep it that way. The lock guards statements, not read-modify-write *sequences*: `params` is one JSON blob, so a caller that reads a job, edits its params and calls `set_params` performs a last-write-wins update that discards anything committed in between. Two writers on one row genuinely exist (the worker recording derived values while `service.jobs.optimize_job` rewrites a budget), so a partial params write goes through `merge_params`, which reads and writes under one hold of the lock.

**Fully offline — the pipeline never touches the network, and the app process never becomes able to.** All model weights load from local paths with `local_files_only=True`; `HF_HUB_OFFLINE=1` / `HF_HUB_DISABLE_TELEMETRY=1` are set in `src/warlock/__init__.py` and must remain the first thing the package does. Never add code that downloads at runtime — a missing weight fails the one job that wanted it, with instructions for the one-time manual `hf download` (see README).

**There is exactly one exception, and its shape is the whole of it: an explicit, user-initiated fetch, in a separate process.** Clicking Download in the app-Settings pane spawns `python -m warlock.pipelines.fetch_worker`, which sets `HF_HUB_OFFLINE=0` **in its own environment only**, fetches one repository, and dies. Nothing about the generating app changes: the parent's `setdefault("HF_HUB_OFFLINE", "1")` is untouched, no module the pipeline imports ever writes the variable (`tests/test_fetch.py::test_only_the_fetch_worker_ever_clears_hf_hub_offline` scans for it), and a fetch is reachable from one button and from nothing on the job path. The subprocess is not squeamishness about a library — it is the only way the guarantee stays *checkable*: `huggingface_hub` reads that variable at **import time**, so an in-process download would mean re-setting it and re-importing a package half the app has already imported, after which "is this process offline" would be a question about import order rather than about one line. It is the `blender_worker` argument applied to a different global. Three consequences are load-bearing. The child goes in the kill-on-close job like every other subprocess (it holds a socket and writes gigabytes; an orphan would fill the disk with nothing on screen to say so). It downloads into a **staging directory beside the destination** and moves the files in only on success, because every presence probe in `fetch.py` answers "is this here" from a handful of filenames and a half-populated directory that happened to contain them would read as a finished download forever — and **the move itself is all-or-nothing for the same reason**, since one `os.replace` per file failing partway (ENOSPC, a locked file) lands in exactly the state staging exists to prevent: `_move_into` backs up anything it would overwrite, and on failure moves everything back into staging and restores the backups, every rollback step under `suppress(OSError)` so it cannot mask the error that caused it. And free disk is checked against the plan's declared size **before** the spawn — refusing the whole plan, the way sweep admission does, because half a plan downloaded is a set of directories the user did not ask for individually.

**Planning a fetch is not performing one, and `fetch.py` is the pure half.** `models.Fetch` is the structured record — repo, patterns, local dir, an optional rename, an approximate size — and **`spec.download` is derived from it** (`models.download_text`), so doctor's paste-able text, the README and what the button actually runs cannot drift; the string could never simply be executed anyway (several entries are multi-command, `pixel` carries a rename and `birefnet` carries a `uv sync` that is a `note` rather than a fetch). Two rules in there are the ones that go wrong silently. **Dedupe is on `(repo_id, destination)`, never on model key** — `dir_name` is not unique, `sdxl`/`sdxl_cfg`/`pixel`/`lightning` are four recipes over one copy of `sdxl-base-1.0` — and an *identical* record arriving again changes nothing, while a genuinely different one against the same destination merges (the IP-Adapter's weights and CLIP vision encoder are two doctor lines and one fetch); without that split, ticking all four SDXL recipes claimed 28 GB. And **paths resolve through `fetch.base_model_dir`**, which `doctor` imports rather than copying: only `turbo` honours `WARLOCK_T2I_DIR`, and the literal `--local-dir models/...` in a command string is the README's spelling of the default root rather than where a fetch goes, so `WARLOCK_T2I_ROOT` relocates a download the way it already relocates a load. Every presence probe lives there too and doctor calls them, keeping one answer to "is this downloaded" behind doctor's several different sentences about it.

**VRAM modes (`Config.vram_exclusive`, queue.py), and the budget is now measured.** Coexist: SDXL-Turbo (~7 GB, fully `.to("cuda")`) and `trellis-server.exe` (~16 GB) stay resident together on the 32 GB card; neither is stopped for the other, and `_maybe_evict_idle` evicts both after the idle timeout. Exclusive restores the sequential handoff for a text job: `trellis.stop()` first, then load and run SDXL, then unload SDXL (`finally`) before trellis restarts. Any change to `Worker._generate` dispatch must preserve stop-before-load / unload-before-next-start **when the flag is set**, or you get an OOM that only reproduces under load, not in tests.

**And "coexist" is a claim about VRAM, which is why an `OFFLOAD` checkpoint hands off unconditionally.** The word was written when every image model was `RESIDENT`. An offloaded spec is the opposite shape: `enable_model_cpu_offload()` keeps the whole ~16 GiB checkpoint in *host* RAM for the life of the pipe and streams one submodule to the device, so its declared `vram_gib` is honest about the card and says nothing about commit — and under WDDM trellis-server's ~16 GiB device allocation is charged against that same commit limit. Three consecutive FLUX.2 klein jobs took Python private commit from 24.4 to 45.2 GiB and system commit to 99%: the 2026-08-03 Resource-Exhaustion crash, reached from the host side rather than the VRAM side. So `queue._needs_handoff` — the one owner of the predicate, now asked from exactly one place: `Worker._acquire_t2i`, the single preamble all four t2i stages (`_generate`, `_pixel_sheet`, `_sprite_synthesis`, `_retexture`) go through, the last three passing the `_ALWAYS_CONDITIONED` sentinel because their conditioning is built per band, per candidate and per view — returns true for the flag, for conditioning beside a *running* trellis, **and for `residency == OFFLOAD` whatever the flag says**, at the accepted cost of a trellis restart per offloaded text job. The give-back is `Worker._release_t2i`, shared by those same three stages; `_generate`'s teardown is deliberately *not* it, because that stage hands straight on to the mesh stage inside the same job and so trades the VRAM against something the others do not (the comment at its own `finally` is the argument). The teardown must be `unload()` and never `trim()`: trim returns the CUDA caching allocator's pool, and none of an offloaded pipe's cost is in that pool. `vram.offloaded_base` is the accounting half — `estimate` prices such a job sequentially — because a gate that charged the sum of two stages that are never resident together would refuse the one checkpoint being careful about VRAM.

**A resource is not released until the last reference to it is gone, and the release helper may not hold one.** `Text2Image.load` builds and configures on a *local* and assigns `self._pipe` as its last statement, with `except BaseException` (a cancel mid-load is the case that most needs the weights dropped) calling `_reclaim`; publishing first meant a failed scheduler swap, device placement or LoRA attachment left `loaded == True` over a half-configured pipe that every later `load()` returned early on, resident and unreachable. **`_reclaim` deliberately takes no pipe argument**: the obvious `_release(pipe)` with a `del pipe` inside frees nothing, because a parameter binding is a live reference for exactly as long as that frame runs and the caller's own local is alive beside it — so every caller drops its reference *first* and then calls. That is measured rather than reasoned: with the argument-taking version the GPU tests' pipes stayed on the card and the next thirty queue tests were refused by dispatch-time VRAM admission. **`TrellisServer.stop()` is the same rule about a process**: `kill()` only asks, Windows reaps asynchronously, and clearing `_proc` regardless meant `running` went false while ~16 GiB was still charged to a live process — into which the handoff then loaded an image model. It `wait()`s after the kill and raises `TrellisStopFailed` if it cannot confirm death, **keeping the handle** (it is the only reference to that process, and `_reap_if_dead` still needs it). The three handoff sites and `ensure_config` propagate; eviction, shutdown, cancel and `ensure_started`'s own cleanup suppress and log, the last for `fetch._move_into`'s reason. And the commit ceiling is re-checked at the **stage boundary** (`_require_commit_headroom`, after the cancel check and before `ensure_config`, the first thing on that path that can lead to a spawn), because the image stage is precisely what moves the number and `_log_mem`'s `log.critical` recorded the wall and then walked into it. Its message says the image is finished and saved and only the 3D stage was withheld — a user told "out of memory" after a successful two-minute generation will otherwise assume they lost it.

Which mode is *chosen* is no longer a guess. `Config.vram_exclusive` is tri-state — `None` means `WARLOCK_VRAM_EXCLUSIVE` is unset — and `studio/runtime.py:_resolve_vram` calls `vram.plan()` after `doctor.run_checks` and **before `_make_worker`**, writing a plain bool back onto the mutable Config; queue.py goes on reading a bool once at startup and knows nothing about it. An explicitly set env var is honoured verbatim and auto-detection never overrules it; unset, a card whose budget (device total minus `vram.HEADROOM_GIB`) cannot hold `TRELLIS_GIB + SDXL_GIB` gets exclusive. A 32 GB card resolves to coexist, i.e. today's behaviour is unchanged, and `tests/test_vram.py` pins exactly that. `bench/runner.run` resolves the same way before the manifest is built, because `vram_exclusive` is a recorded field and "auto" is not comparable across runs.

`vram.py` is the measurement everything above was missing, and it is pure in the way `memlog.py` is: no imports from `service`/`queue`/`studio`, `None` rather than an exception when a reading is unavailable, and `WARLOCK_VRAM_TOTAL` standing in for a card so the whole gate tests headless. `device_memory()` reaches torch through `sys.modules` (as `queue.vram_gib` does, and for the same reason) but wraps `cudaMemGetInfo`, so unlike `vram_gib` it *does* see trellis-server's allocation in the other process. The cost table is prose that became numbers — every constant in it was already asserted in a comment in queue.py or text2image.py. **`Plan.explicit` is carried, not re-derived**, and `Config.vram_exclusive_explicit` is what carries it forward: the resolve writes a plain bool over the tri-state, which destroys the evidence, so every later `plan()` call — every health poll, the doctor row — saw a set value and reported an auto-selected mode as "set explicitly by `WARLOCK_VRAM_EXCLUSIVE`". Every caller that resolves a config the startup pass has already touched passes `explicit=`.

**Admission control is at the door, and refusing is the point.** `service.validation.check_vram` runs in `create_job` (after the seed checks, before `_decode` and any file write, so a refused request leaves no `input.png`) and in `promote_to_model`, and raises `Invalid` with a message naming the number *and a remedy the user can act on* — the conditioning to turn off, the resolution to drop, `WARLOCK_VRAM_EXCLUSIVE=1`. `Worker._check_resources` re-checks at dispatch against free VRAM (secondary: on WDDM the driver's free figure is virtualized) and against `memlog`'s commit fraction, refusing past `COMMIT_CEILING`. That last one is not a nicety: overcommitting VRAM on Windows does not raise, it spills into shared system memory and becomes host commit, which is the 2026-08-03 Resource-Exhaustion crash. A job that fails is the good outcome. `check_weights` joins it there and answers the other half of "can this run": a text job whose selected checkpoint, style LoRA, adapter or ControlNet is not on the host is refused with the exact `hf download` line doctor already knows, rather than queueing, waiting its turn, loading and dying with a diffusers traceback naming a directory. Only text jobs, because only they touch SDXL; and deliberately *not* the two fatal rows, because a host missing those has a red banner at startup and re-refusing every submit says the same thing in a worse place. **The style LoRA is the case that justifies the whole check**: `_load_loras` *skips* a missing style adapter where it *raises* on a missing base LoRA, so without this the job finished, looked wrong, and carried a `style_lora` param claiming a style that never ran -- and `style_lora` is in `VECTOR_PARAMS`, so that row then joined the findings corpus as evidence about it. **Every door onto a run takes both halves, and finding the ones that took only VRAM is a recurring bug.** `create_job`, `promote_to_model`, `rerun_job` and `start_pixel_sheet` all admit on weights as well as on the plan; the last two were checking VRAM alone until 2026-08-11. A reroll matters as much as a first submit and for a reason a first submit does not have: the source row was admitted against whatever was on disk when it was *submitted*, which can be days and a pruned models directory ago. A pixel sheet's door had the subtler gap — it checked that the base and `models.PIXEL_SHEET_LORA` *fit* each other and never that either was present, and the worker's own tolerance then logged, restyled bare, and wrote a sidecar naming a LoRA that never loaded. The base-model half of the refusal is one function (`validation.check_base_model_weights`) called from all three of `check_weights`, `sprites._check_weights` and the sheet door, because it is one sentence and one `field="base_model"`, and three copies of it is how one of them comes to be relaxed alone.

**A refusal names the control it came from, and library text never reaches the user unframed.** `service.errors.Invalid` has carried a `field` since it was written and the UI highlights what it names -- but the nine `raise Invalid(str(exc))` passthroughs could not supply one, so the app's most common refusals arrived pointing at nothing. `guidance.GuidanceError` is a **`ValueError` subclass** carrying `field`, which is what let every one of them gain an address without touching a single `except ValueError`; `errors.invalid_from` wraps a library exception in a sentence naming what was being done and carries the field through. Recovering the field by parsing the message was the alternative and is the `judge.STAGES`/`verdicts.STAGES` hazard: two spellings of one fact, drifting the first time a message is reworded. `validation.not_done_message` and `files.unready_reason` are the same rule applied to two sentences that were true of five situations each -- "reference is queued" and "file not ready" -- and `unready_reason` is deliberately a *second* function rather than folded into `ready`, which stays the gate and the authority: it runs only on the refusal path, so a sentence that disagreed with it is a slightly wrong explanation rather than a wrong permission, and folding it in would put string formatting inside the per-row listing loop `attach_files` exists to keep cheap.

**A doctor probe that cannot give its memory back runs in a child.** `pipelines/loadprobe.py` answers "does this checkpoint actually load" for the host matting and pose models -- the question the rows used to decline with "not checked" -- and it is a subprocess for a measured reason, not a stylistic one: loading BiRefNet on the CPU costs **1475 MB** of RSS, and after every reference is dropped and `gc.collect()` has run, **1053 MB is still resident**, because what holds it is the allocator's arenas rather than a live object (`docs/measurements/2026-08-08-load-probe-memory.md`). An in-process check is therefore a gigabyte spent on every launch, for the life of the process, on a user who may never do a 2D export -- against an app whose worst crash is host-commit exhaustion. It also dragged torch into the app process by a different door than the one C29 closed. This is `_probe_blender`'s shape and the third instance of one rule: `bpy` is process-global, `HF_HUB_OFFLINE` is import-time, and RSS is unreturnable, so all three are paid in a process that ends. `winjob.run`, like every other spawn.

**The fourth instance is the matte itself, and it is persistent rather than one-shot.** The same measurement condemns the *inference* path for the same reason: `matting.unload()` cleared a dict and returned about a third of what the load cost, so a session that did one 2D export held a gigabyte until it closed. `pipelines/matting_worker.py` is the child and `unload()` now kills it, which is what finally makes the name true — reached from `queue.Worker._maybe_evict_caches` past the idle timeout, through `asyncio.to_thread` because it is a process kill, alongside `pose2d.unload` (kept in process: small, CPU-only, and moving it out is not justified without its own measurement) and the new `bench.metrics.unload`, which is the one of the three that can hold **VRAM** — its cache key carries the device and the benchmark path resolves `None` to cuda. That eviction is latched on `_caches_evicted` and stamped off the last finished job, because none of the three records a `last_used` and an unload of an empty cache is a no-op worth no thread at all. It is **persistent** where `loadprobe` is one-shot because `derive.get_file` mattes one artifact per call and an asset's icon, sprite and pixel sets are three calls — a one-shot child would pay the load three times. Four rules under it. The boundary is inside **`_model_mask`**, not at `mask()`, so the three-source preference order, the never-fatal fallback and every caller are untouched and a spawn failure, a timeout or a dead child is an exception `mask` already answers with the corner flood fill. Pixels travel as **files** (`blender_worker`'s rule, and here also because a 4096-square matte is 16 MB against a 64 KB pipe buffer); only a marked one-line JSON status crosses the pipe, with the child pointing `sys.stdout` at stderr so a print from `transformers` or BiRefNet's own modelling code lands in the log stream rather than mid-response. The **failure memo stays in the parent** — `_FAILED`/`_last_error` must outlive the child's death, or a broken install costs a spawn and a load per image in an export loop — and only a `stage == "load"` answer memoizes, because one image that failed to matte says nothing about the next. And `matting._infer` is the arithmetic half, kept in `matting.py` beside the constants and the docstring arguing for them and *imported* by the worker, exactly as `blender_worker` imports `rigging.fit_template`.

**`hole_worst` is corpus-dependent, and nothing in the UI may imply it is a quality scale.** It was *inverted* on the 2026-08-07 corpus -- AUC(`hole_worst` -> reject) 0.115, not weakly informative but **backwards**, with 48 of 81 rejected meshes measuring exactly 0.0 and none of the 3 accepted ones -- because the dominant failure mode there was a solid slab and a slab has no visible openings. **On the 2026-08-09 re-baseline it reads the right way round: AUC 0.756, one mesh of 41 at exactly zero** (`docs/measurements/2026-08-09-rebaseline.md`). Nothing about `meshaudit` changed; `bg_removal` did. The slab was an artefact of the `auto` matte, and under birefnet it is gone. **That is the invariant, and it is stronger than the inversion was**: a scalar whose AUC moves 0.64 because an unrelated knob moves is measuring whatever the corpus's dominant artefact happens to be, so a *low* reading is never evidence of quality on its own and a figure quoted without its corpus means nothing. So `widgets.quality_badge` still has **no green branch** below `AUDIT_UNINFORMATIVE` -- the re-baseline's own rule defers that flip to its own measurement and explicitly does not take it, n=41 on one subject and one prompt being no grounds for telling a user a low hole count means a good mesh -- the inspector still says "a solid, featureless mesh scores this too" under a low figure, and the band-sweep table still does not state "lower is better" as a general rule (it is still the right ranking *there*, where every row is one subject at one seed). The escalation is kept, because a high reading is real evidence on any corpus. This is the same doctrine `judge.py` is written under and the reason the probe is trained on pixels rather than on the audit scalars -- an argument the re-measurement strengthens rather than retires, since a probe fitted to those scalars would have learned the slab in August and something else a fortnight later.

**`config.effective` is the one answer to "what is this process running on".** `warlock doctor` prints it and the diagnostics popup draws it, and its value is the `from_env` column rather than the values: an install whose behaviour disagrees with the manual almost always disagrees because something in its environment says so. It reads `os.environ` rather than diffing against a freshly constructed `Config`, because the diff reports "default" for a variable explicitly set to the default value -- which is exactly the case where somebody is asking whether their setting took. `config.SETTINGS` is a written-out table (every default is a `default_factory` lambda closing over its own variable name, so there is nothing to derive it from) asserted against the dataclass in both directions, with `vram_exclusive_explicit` the one stated omission because it is derived by the startup resolve rather than configured.

**A manual chapter's number decides both its order and its part, so adding one is a renumbering.** `loader.PARTS` maps number ranges onto part headings and `chapters()` sorts by filename, so a chapter appended at the end wears the wrong part or grows a second heading with the same name. Renumbering is the supported move and it is mechanical rather than risky, because `tests/manual/test_docs.py` asserts the chapter list, every cross-link, every anchor, the index's links and `HELP_TARGETS` -- in both directions. `tests/manual/test_coverage.py` adds the direction those could not see: a pane with neither a (?) nor a stated exemption fails, which is what "the manual documents this and nothing reaches it" looked like before.

**Every subprocess goes in the kill-on-close job, without exception.** `winjob.run()` is `subprocess.run` with the assignment in the gap between spawn and wait, and it is what `doctor._probe_blender` and `pipelines/optimize` use — the two short-lived children that were spawned unassigned and could outlive a hard kill (the bpy probe runs during `Runtime._start`, so killing Warlock while it starts stranded a python.exe mid-`import bpy`). `tests/test_vram.py::test_every_subprocess_spawn_is_in_the_kill_on_close_job` scans the package and fails on any `subprocess.Popen`/`run` call site without a nearby `winjob.assign`. The guarantee is also *visible* now: `winjob.armed()` backs a doctor row, because a host where `_ensure_job` quietly failed used to be indistinguishable from one where it took.

**`source.glb` is the reconstruction; `model.glb` is derived from it.** trellis writes `source.glb` and nothing ever overwrites it — `model.glb` is produced by optimize-then-normalize, which is why `service.jobs.optimize_job` can retarget a triangle budget without another two-minute trellis run. The ordering is load-bearing in one direction only: gltfpack rewrites the node graph, so it must run *before* `normalize_glb` inserts the scale/translation node, and `optimize_job` reapplies the transform for exactly that reason. `_discard_artifacts` deletes **both** files, or a cancelled job could be re-optimized back into existence. Everything else (STL, OBJ zip, FBX, `collision.glb`, `textures.zip`) is a pure function of `model.glb`, derived on first request under the per-artifact `_convert_locks` idiom, and `optimize_job` deletes all of them because they describe the old mesh.

**Nothing is ever written directly onto a name something else may already be reading.** Every write that lands on a *served* file goes through a staging name beside it and an `os.replace`, with the unlink in a `finally` — `service/derive.py::_staged` is the canonical spelling and the one the module's own derivations call rather than re-implementing. The rule is not only about concurrency, and the sharper half is freshness: for several artifacts **existence *is* the freshness test**, so a writer that dies part way through does not merely expose a torn read for a moment, it leaves a truncated file that is served under that name for the life of the job directory, with no way for a retry to get past it. That is what a Blender killed by `pose_timeout` or by kill-on-close leaves behind, and it is why `model.fbx` (`service/derive.py`) and a baked pose GLB (`service/rig.py`) are staged rather than exported in place. The same discipline covers the rig QA sheet (`queue._deform_qa` — where a *re*-rig packs a new atlas while the previous run's `rig_qa.json` already satisfies `files.ready`, so the marker promises a whole sheet over a half-written one), `thumb.png`, and `input.png` on the reference-reroll loop, which rewrites a served name once per rejected attempt. A staging file is a dotfile and **nothing ever sweeps one**, so the `finally` is as load-bearing as the rename: a failed encode that strands its temp leaves it there until the job is pruned.

**Grounding is not conditional on a size.** `normalize_glb` scales (only when `size_m` was asked for), centres X/Z and puts min-Y at zero on *every* job — a pivot at the reconstruction volume's centre is a manual fixup on every Godot/Unity import regardless. Because it now runs on meshes it never used to touch, a failure is logged and swallowed rather than failing a job whose GLB is already on disk — the same rule `_audit_mesh` and the report follow. `scale_glb` survives only as a thin wrapper.

**And grounding composes `T · S · M_root`, never `M_root · T · S`.** The bounds are measured in *world* space, so the transform has to apply outside each root's own — which is why `_insert_transform_below` **empties the root** and folds its TRS into the inserted child (`_composed`; TRS decomposes exactly because the scale is uniform, and a `matrix` root composes as a matrix). Sandwiching the grounding under an untouched root was wrong twice: a rotated root rotated the grounding offset, and applying the same world-space translation once *per root* while each root's offset stayed unscaled above it meant a Clay export — which emits **one root per object** — grounded every object as though it alone were the scene, so three boxes asked for 2 m came out 8.2 m and reported 2. trellis output hid both, because trimesh writes one identity root. The transform still may not sit *on* a root (trimesh treats one as the base frame and discards it, which would leave the GLB grounded and the derived STL/OBJ not), and a wrapper node above the roots does not work either: trimesh's base frame is named `world` and so is the root its own exporter writes, so the collision resolves into a cycle that drops the transform again. `tests/test_postprocess.py` pins the whole matrix — identity / rotated / translated / non-uniformly scaled / matrix / multi-root, with and without `size_m`.

**The composed SDXL prompt is chunk-encoded, not truncated.** CLIP's text encoders cap out at 77 tokens, and with twelve optional guidance fields the composed prompt routinely exceeds that. `pipelines/prompt.chunk()` splits it into multiple <=77-token chunks on comma boundaries (never mid-phrase), each encoded separately and concatenated on the sequence axis in `pipelines/text2image._encode_long_prompt` -- the UNet's cross-attention has no sequence-length limit, only the text encoders do. A single-chunk prompt (the common case) is bit-identical to the old direct-string path. Guidance fragments in `guidance.py` stay 2-4 words each regardless: chunking removes the hard ceiling, not the soft one where a longer sequence dilutes cross-attention.

**A native kernel is an optimisation with a reference, never a replacement.** `native/*.c` builds to `vendor/warlockc/warlockc.dll` (gitignored, like every other vendored binary) and `native.py` is the ctypes loader — pure in the way `vram.py`/`memlog.py` are: stdlib only, no imports from `service`/`queue`/`studio`, `None` rather than an exception when the library is missing or unusable. Every call site reads `if native.available(): ... else: <the numpy code>`, and **the numpy code is never deleted** — it is both the fallback on a machine with no compiler and the reference the parity tests measure the kernel against, which is why `meshaudit._fill` survives as a whole function nothing calls on this machine. The bar for a float kernel is a **bit-identical** result, not a close one, which is what `/fp:precise` (MSVC) and `-ffp-contract=off` (clang) in `build.ps1` are for: an FMA rounds once where numpy rounds twice, and that moves a triangle edge by a pixel. **clang-cl needs both spellings**, and that is the trap: its `/fp:precise` implies `-ffp-contract=on` on clang ≥14, so the flag that makes MSVC exact makes clang-cl permit exactly the FMA the bar forbids — the branch passes `/clang:-ffp-contract=off` alongside it. Nothing else would catch that: the ABI handshake compares a version, not arithmetic, so the only symptom is a parity test failing on one compiler. `WARLOCKC_ABI` in `warlockc.h` must match `native.ABI`, because `vendor/` being gitignored means a checkout routinely holds a DLL built from older sources — an absent DLL is obvious, a stale one silently computing last week's answer is not. Tests that are *about* the numpy path pin it with a fixture rather than trusting this machine not to have a DLL, and the suite is expected to pass both ways (`WARLOCK_NATIVE=0`). Two things the inker compositor's kernels (`native/composite.c`, behind `composite.over`/`paint_colour`/`stack_region`) added to that rule and neither is optional. **A whole-region decision stays in Python**: `over`'s early-out is `every source alpha is 1`, a reduction rather than a per-pixel test, and an opaque pixel *inside* a non-opaque source goes through the full formula — so a per-pixel shortcut in C would diverge in the last ulp, and the fused `stack_region` kernel is instead *told* which layers took it, as `WARLOCKC_BLEND_REPLACE`. And **`composite._MODE_IDS` is written out, not `enumerate(BLEND_MODES)`**: an automatic index would hand the kernel a number no `case` matches and get `normal` composited back for it, silently, whereas a name the map does not carry simply falls back to numpy. The same reasoning is why a kernel that fuses `u8/255.0` into its loads builds a 256-entry table of that exact expression rather than multiplying by a reciprocal. **`native/contours.c` is the one kernel whose bar is not identity to the reference's output, and the licence for that is in the reference**: `SelectionMask.contours()` leaves loop order, starting vertex and winding unspecified (`_chain` starts from `next(iter(set))`), and at a checkerboard corner — where two regions touch diagonally and four boundary edges meet — the tracer's left-turn rule and the reference's dict order partition the *same edges* into different loops. So `tests/inker/test_contours_native.py` asserts the **set of unit edges**, plus closure and unit steps and the reference's `len(loop) > 2` floor, and asserts the loop *count* only on masks with no diagonal corner in them. A loosened bar is otherwise how a kernel quietly stops being checked, which is why this one is written down beside what makes it sound. Two consequences of the walk that look like bugs and are not: a loop legitimately passes through the same vertex **twice** at a pinch (one region touching itself diagonally), so the walk ends when it arrives back at its start rather than after a vertex count; and the kernel allocates nothing, so the caller sizes the point buffer from `_boundary_edges` — an *exact* count of the boundary edges, not an estimate, which is why a `-1` means fall back to numpy rather than retry bigger.

**Two different mesh measurements, deliberately not merged.** `meshaudit` answers "can you see through it" (a silhouette check, what a player notices); `meshreport` answers "will an importer accept it and will it sit on the floor" (topology, materials, budget, pivot). Only the second may use the word *watertight* — the badge used to apply that word to the first, which it never proved. Both are stored on the job and `params["mesh_audit"]` keeps its old shape so existing readers are unchanged.

**gltfpack is vendored and present; the named tiers are unqualified, and that is now the only reason `raw` is the default.** `vendor/gltfpack/gltfpack.exe` landed on 2026-08-07, so `pipelines/optimize.py`, the config field, the non-fatal doctor check and the API are all live rather than dormant — which means the constraint changed shape rather than going away. A named tier is no longer a button that *fails*; it is a button that silently ships a worse mesh, which is harder to notice. So the bar stands unchanged: a tier stays out of the generate form until it has been run against a chest, a sword and a rock and shown to keep UVs, both PBR maps and material assignment. `Config.mesh_profile` defaults to `raw` and `panes/settings_3d.PROFILES` offers `raw` alone for that reason and no longer for the missing binary. The retarget control (`studio/panes/retarget_panel.py`, in the inspector under "Triangle budget") is the qualification path: it offers only `raw` while `vendor/gltfpack/gltfpack.exe` is absent and the whole tier list once it is there — which is today — so a tier can be exercised without being exposed to a generate form. `service.jobs.optimize_job` refuses a job that is still `queued` or `running` with a `Conflict`, because its half of the write takes a lock the worker's `_optimize`/`_apply_scale`/`_audit_mesh` do not. It also resolves its tier through **`_resolve_profile`, the same one `create_job` uses**, rather than calling `optimize.resolve` itself: the second copy raised a fieldless `Invalid` and skipped the gltfpack-presence refusal, so a retarget on a host whose binary was broken silently shipped the raw copy while `params["profile"]` named a tier that never ran — and `profile` is in `VECTOR_PARAMS`, so that row then joined the findings corpus as evidence about a tier nothing had run. Writes onto a served `model.glb` are always staged (`optimize.staged_copy`, `postprocess._staged`) — `optimize_job` runs on *done* jobs, so a bare `copyfile` would let a concurrent read see a truncated file — and it reports (never deletes) the rig artifacts a retarget makes stale, which the retarget panel warns about before the button rather than after.

**Blender never runs in the app process.** `bpy` is process-global, not thread-safe, and hard-crashes (rather than raises) on some non-manifold geometry — which trellis output frequently is. So it runs out-of-process as `python -m warlock.pipelines.blender_worker`, mirroring the `trellis-server.exe` subprocess pattern. `rigging.py` is the host side and must stay importable with no bpy anywhere; `pipelines/blender_worker.py` is the only module allowed to `import bpy`, and it imports `rigging.fit_template` so host and worker can never disagree about where a joint goes. The single-sqlite-connection / single-event-loop invariant is untouched by this: `rigging.run_worker` is blocking and every caller dispatches it through `asyncio.to_thread`.

**A rig writes into the *source* job's directory, via temp names.** `rig.glb`/`rig.json` land next to the `model.glb` they were fitted to, not in the rig job's own dir — the rig belongs to the mesh. The worker never writes the served names: `rig_spec` points it at `.rig.tmp.glb`/`.rig.tmp.json` (the `.glb` suffix is load-bearing — Blender's exporter appends one to any filepath without it) and `rigging.finalize_rig` renames them into place on success, GLB first so `rig.json` — the completion gate `_attach_files` and the file route key on — never advertises a mismatched GLB. That gate alone is not enough on a *re-rig*: the old `rig.json` already satisfies it while Blender is writing, which is exactly why the temps exist. Consequences that are easy to get wrong: `Worker._discard_artifacts` must resolve `params["source_job"]` when cleaning up a cancelled rig (deleting `model.glb` there would destroy a different, successful job's mesh) and deletes **only the temps** — a cancelled re-rig must never destroy the previous successful rig's artifacts — and `queue._rig` skips `finalize_rig` when the cancel event is set, so a cancel after the solve finishes doesn't publish anyway.

**A rig welds before it heats, and every rung of that chain names itself.** trellis meshes are UV-atlased, and an xatlas seam split is a non-manifold edge that is not a hole — the same root cause that had `meshreport` measuring seams and calling them holes, addressed there in the *measurement* and here in the *solve*. So `blender_worker._skin` merges coincident vertices (`weld_distance`, which is `meshreport.WELD_TOLERANCE` of the bbox diagonal — imported, not restated, because it is one judgement about one mesh), recalculates normals, and only then attempts `ARMATURE_AUTO`; the chain is weld → verify → unwelded heat → envelope, and envelope is still the floor. The weld must be invisible to the user, and the whole argument that it is rests on merge-by-distance keeping face-corner data — UVs are per-loop, so the two halves of a seam keep their own coordinates while sharing one position — which `tests/test_rig_weld.py` proves against a real Blender by comparing exported texture bytes and the per-loop UV set across the weld rather than accepting that it looked fine. Two decisions are pure so a test can reach them without bpy, exactly as `_rig_bones` is: `weld_distance`, and `_skin_steps`, which is where **a weld that merged nothing is reported as plain `automatic`** — the mesh the solve saw is the mesh it would have seen anyway, and there is no second, identical attempt to fall back to. The pre-weld datablock is kept and put back for the unwelded rung, because a welded solve failing is not evidence the unwelded one would. `automatic-welded` joins `weighting`'s vocabulary additively; the reason string names every rung that failed, since "it failed" sends the reader looking at the weld when it was the geometry.

**The deformation battery is data, rendered through the one sheet pipeline, and it scores nothing.** `src/warlock/templates/deform_qa/<template>.json` holds the poses a rig is *reviewed* in — squat, arms overhead, elbow and knee at 90°, torso twist — in the same normalized-JSON spirit as the skeleton templates and the same local-quaternion format as the shipped pose presets, because `queue._deform_qa` renders them through `sheetlib.plan`/`pack`/`sidecar` around `op_sheet` and nothing else: a second renderer would be a second set of camera conventions to keep in agreement with the first. It is a separate directory from `src/warlock/templates/poses/` because these are not poses anybody would ship an asset in, and the rows carry synthetic ids (a sheet row is keyed by `(pose id, frame)`, so a battery of id-less rows renders the first pose into every row). The output is `rig_qa.png` + `rig_qa.json` in the **source** job's directory beside `rig.glb` — deliberately not a sheet in `sheets/`, so it never joins `list_sheets`, counts against `MAX_SHEETS` or dies with a sheet delete — served only once the sidecar exists, which is the `rig.glb`/`rig.json` ordering again. A failure is logged and swallowed (`_audit_mesh`'s rule: the rig is already published), a template with no battery renders nothing, and `Config.deform_qa` is a kill-switch rather than an opt-in for the reason `pose_fit` is one. **Nothing scores it.** The point is a picture a person looks at; a metric would be a claim about deformation quality that nothing here has earned yet.

**Where a joint goes has three sources, in a fixed order, and the third is wholesale or not at all.** `rig_spec` takes `bones` (world-space joints the *user* moved, already through `validate_joints`), `template_bones` (the template's own normalized landmarks, replaced with ones measured off the reference image) and neither, and `blender_worker._rig_bones` is the single place that decides between them — its own function precisely because everything around it in `op_rig` needs bpy, so that decision is the part a test can reach. **The measured landmarks are a better *template*, never a second fitter**: they are still normalized, still the template's names and parentage, so the worker scales them with the same `fit_template` and the bbox scaling stays owned by one side. `pipelines/pose2d.refit` is that mapping (COCO-17 → the humanoid template), split from the model half the way `reference.py` is split — arithmetic on landmarks, stdlib only, so every rule about where a joint lands is assertable from synthetic numbers, while torch stays inside `_load`/`_detect` because `available()` is the question every caller asks first. **Depth is the template's for every joint**, since one view fixes x and z and says nothing about y. The premise is that the mesh *is* `input.png` reconstructed, which is also why the person box comes from `reference.measure` rather than a detector: the composition gate has already established one subject and already measured its silhouette. **Any doubt refuses the whole fit** — a landmark under `MIN_KEYPOINT_CONFIDENCE`, one the detector never produced, a figure whose knees are above its hips, a landmark outside the subject bbox past `BBOX_TOLERANCE`, a template outside `POSE_FIT_TEMPLATES` — and never per-joint: an arm measured against the subject beside a shoulder assumed from a T-pose is not partly better, it is a skeleton internally inconsistent in a way nothing downstream can detect. `Worker._wants_landmarks` gates on cases where the answer *could not be used* (wrong template, kill-switch, corrected joints already present, no `input.png`, no weights) and never on how good it might be, which is `refit`'s business; `_landmark_bones` runs in `to_thread` and log-and-swallows like `_audit_mesh`, because the artifact this could fail is one the user asked for and the improvement is one they did not. `rig.json` gains `fit` — additive with no version bump, since every reader is `.get`-based — and `adjusted` still means only "the user moved these".

**A pose is a map of glTF node-local quaternions, and that is the whole contract.** The viewer never sees a Blender bone and the worker never sees a viewer joint node; they agree because both talk about the joint node's *local* rotation. Blender composes a posed bone as `pose(b) = pose(parent) @ (rest(parent)⁻¹ @ rest(b)) @ basis(b)`, and a glTF joint's local transform is `pose(parent)⁻¹ @ pose(b)`, so `node_local == rest_node_local @ basis` exactly — `blender_worker._rest_local_rotation` is that one line, and no per-bone axis correction is involved (the Z-up→Y-up flip cancels because the exporter applies it once at the root). Two things keep the identity true and both are load-bearing: the worker imports with `bone_heuristic="BLENDER"` (the default re-aims bones at their children and silently changes `matrix_local`), and exports with `export_rest_position_armature=False` (the default writes every joint at rest and demotes the pose to an animation track). Quaternions are stored XYZW (the order `THREE.Quaternion.toArray()` used, kept because every pose on disk is in it); the worker converts to WXYZ. `studio/viewer/pose.py` imports `rigging.mirror_quaternion` rather than reimplementing it -- the browser's copy carried a comment insisting the two stay identical, which is exactly the sign convention that is wrong in a way a still image cannot show. `tests/test_rigging.py::test_a_posed_glb_carries_back_exactly_the_rotations_it_was_given` pins it by reading the exported GLB's JSON chunk directly, not through bpy.

**Poses are files, not rows.** `<job_dir>/poses/<pose_id>.json` (one per pose, so a save needs no read-modify-write and therefore no lock) with the baked `<pose_id>.glb` beside it. `rigging.pose_path` is the *only* place a caller-supplied pose id becomes a path and it raises on anything that isn't `[0-9a-f]{12}`. Overwriting a pose deletes its cached GLB — the bake depicts the old rotations. The bake itself is derived on demand in the request under the same `_convert_locks` idiom as the STL/OBJ exports, not on the job queue: it is a one-second subprocess, and putting it behind the serial GPU queue would make it wait on a trellis run.

**A sprite sheet's grid is decided on the host, never in Blender.** `pipelines/sheet.py` is pure — `plan()` works out the cells, `pack()` composites them with Pillow, `sidecar()` writes the JSON — and `blender_worker.op_sheet` only renders one square transparent PNG per cell into a scratch directory. That split is what makes the grid testable without a GPU and keeps the in-app preview, the renderer and the sidecar from disagreeing. The preview's own camera math lives in `studio/viewer/sheet.py` and has to agree with it: yaw 0 on +Z, extent `max(hypot(sx, sz), sy) * 1.12`. That margin has **one owner**, `pipelines.sheet.FRAME_MARGIN`, which the worker and the preview both import — it used to be two hand-written literals holding up an agreement the module docstring merely asserted, beside a `spec.get("margin", 1.12)` nothing ever wrote a `margin` into. The dead indirection is gone rather than made real: a per-spec margin is a second way to frame a sheet that the preview could not see. Three details that are easy to undo: the camera is framed **once** from the rest bbox (reframe per pose and the subject jumps between rows); the sidecar carries a **flat `cells` list** so an animated clip becomes more cells with `frame > 0` rather than a format v2; and cells arrive grouped by row so the worker re-poses once per pose, not once per frame. Column 0 is the front view — yaw 0 looks along +Y in Blender, and the templates put the subject's forward at −Y.

**Blender's glTF importer invents objects you must ignore.** It parks bone-shape widgets for an imported armature in a collection named `glTF_not_exported`. The collection is excluded from the *view layer*, so nothing renders and nothing re-exports — but the objects are still in `scene.objects`, and a unit icosphere among them trebled `_scene_bounds` and framed every rigged sheet's subject at a third of its size. Every `import_scene.gltf` in the worker is followed by `_purge_import_helpers`.

**Derived values never survive into a new job, and inputs are bounded at the door.** `service.validation.DERIVED_PARAMS` is the single strip list for rerun/promotion — anything the worker records about a finished job's *artifacts* (`composed_prompt`, `mesh_report`, `transform`, …) must be added there when introduced, or a reroll wears a quality verdict about a mesh that doesn't exist yet. On the way in, `create_job` enforces the caps next to it (`MAX_UPLOAD_BYTES` 20 MB before decode, `MAX_IMAGE_PIXELS` 16 MP from the header before pixels decode, `MAX_PROMPT`, seeds 0..2³¹−1 via `_check_seed` on every route that takes one) and removes the job dir it pre-wrote if the DB insert fails — `input.png` is deliberately written before the row exists, so the cleanup is the other half of that ordering.

**A renamed taxonomy key is an alias, never a removal.** `guidance._LEGACY_ALIASES` maps every key that has been renamed onto the one that replaced it (`platform`'s old hardware tiers onto `2d`/`3d`, `art_style`'s abstract names onto the console eras), and `_lookup` and `compose_prompt` both go through `_canonical`. Both halves are load-bearing and for different reasons: `_lookup` is what rerun and `promote_to_model` re-normalize stored params through, and an unknown key there is a `ValueError` the API turns into a 400 — so without the alias a rename silently makes every asset already on disk un-rerollable and un-promotable; `compose_prompt` deliberately *skips* unknowns rather than raising, so without the alias there a legacy row keeps working but quietly composes a weaker prompt than it did. `normalize` writes the canonical key back, so params migrate the first time a job is touched. The accepted cost is that findings and verdict buckets split across the two spellings, because a vector recorded before the rename is a different string — evidence under the old name simply stops accumulating, which is why a rename is a real decision rather than a relabel.

**A global binding is checked above the modes, which is what makes it Alt and not Ctrl.** `modes.mode_for_digit` maps Alt+1..8 onto the switch positionally, and `_shortcut` answers it -- along with Ctrl+K's command palette, F1 and F10 -- *before* the `WORK_MODES` gate, because Inker, Clay and Review consume every key they are given. That ordering is the whole argument for the modifier: whatever a global binding names, it takes from those three permanently, and Inker already binds Ctrl+0/Ctrl+1 to its zoom while Clay's planned axis views want Ctrl+1/3/7. **Esc leaves the three pass-through modes** (Home, Manual, app Settings) for the mode it came from, and `App._note_mode` samples that pair **once per key event rather than once per frame** -- F1 changes the mode from inside `_shortcut`, so a frame-start sample would still be holding the mode from before it and Esc would go two steps back. Home is the floor rather than a place you escape from: the app opens on it, so there is routinely nothing behind it. `studio/palette.py` is the palette's pure half -- commands, subsequence match, ranking, stdlib only -- and its mode commands are **derived from `modes.MODES`**, because a palette is a second index of everything the app can do and a hand-written one drifts; switching is `state.set_mode`, the one function `App._set_mode` also calls, after the palette's own copy drifted in the way that matters -- it lacked the early return on `key == state.mode`, so re-selecting the current mode set `previous_mode == mode` and the next Esc fell back to Home. Home's chooser tiles are the third index of the same list and are checked against `modes.WORK_MODES` for coverage, names and order left editorial; a command that cannot run right now is *listed and greyed*, since an empty result teaches neither that it exists nor which mode owns it.

**`ConfirmQueue` and `PromptQueue` really queue, and `pending` is the head rather than a field.** They used to keep one slot and drop anything that arrived while a question was up, on the reasoning that the user cannot act twice between frames -- true of *clicks* and false of a finished task landing beside one, and false of any path that asks more than once. Assigning `None` to `pending` was how a caller cancelled, which on a queue would silently discard everything behind it too, so it is read-only and `dismiss()` is the operation. `_request_quit`'s three hand-nested lambdas became a list walked by index; the *chain* stays, because it is the semantics rather than the workaround -- asking all three side by side would mean clicking "Keep editing" on the first still left two questions to dismiss. A modal owns the keyboard while it is up (`App._modal_open`), or one Esc both cancels the dialog and leaves the mode behind it; releases still pass, because Inker's space-to-pan is a hold and would otherwise latch.

**Four toast levels, and the ladder is reading time rather than severity.** `state.TOAST_LEVELS` is the table -- info and success share a dwell because a confirmation is read at a glance, a warning is a sentence, an error usually says what to do next. An unrecognised level renders as an ordinary notice, the rule `Toast.action` already followed and what lets a level be raised before `widgets` has heard of it. Hovering *pauses* a toast by pushing `born` forward by the frame's delta rather than by recording a pause timestamp: age is read from `born` in four places and a second field saying "but not that age" is how two of them come to disagree. `state.toast_log` is the session's history, in the diagnostics popup rather than behind a bell of its own -- it is the same question as "what is wrong with my install" asked about the last ten seconds -- and it holds the `Toast` objects, because a list of strings could not say what level a message was. A sweep raises exactly **one** toast (`jobs_cache.sweep_summary`), judged against the *loaded* window, which is a stated limitation that fails in the safe direction: an early summary is a slightly wrong number where a missed one is silence at the end of an overnight run.

**A filter box that is also a query, and a sort that admits what it cannot answer.** `state.parse_query` splits `tag:`/`status:`/`kind:`/`stage:`/`id:`/`name:` out of the library's text box, and **an unrecognised prefix stays free text** -- silently reinterpreting a colon somebody typed on purpose is how a search starts returning nothing with no explanation. Field terms *add* to the combos rather than overriding them, so `status:error` with the status combo on *done* correctly shows nothing. `Filters.order` offers six keys, every one stable within a tie, and every one buckets its **unanswerable** rows at the end in both directions -- the rule `best` already followed for an unranked job, generalised, because "unknown" is not a value at one end of a scale and filing the unmeasured backlog under "smallest" would be a wrong answer rather than a partial one. Size reads the deferred storage walk, which is why `JobsCache` carries a `_sizes_generation` the memo keys on.

**The trash is a column, and Delete stopped asking.** Migration 9's `deleted_at` makes `Filters.trash` a *view* rather than a filter -- everything else narrows what you are looking at, this changes which set you are looking at -- and the files stay on disk, which is the whole feature. `library.delete_asset` trashes and keeps its name at every call site: what the user asked for is "get this out of my library", and the reversibility of that is a property of the app rather than of each call site; `purge_asset` is the permanent one and only the trash reaches it. The card's Delete raises no confirm, because the trash *is* the confirmation and an undo available an hour later beats a question answered in half a second while looking at something else -- the irreversible paths keep theirs. **Trashing a queued job cancels it**: deleting used to remove the row so the worker's poll never saw it again, and a trashed row is still a row. `empty_trash` reads `store.trashed()` rather than a page, since "empty" that left the older half behind while reporting success is the worst reading of the word. Prune deliberately still deletes from disk -- one that trashed two hundred jobs would free nothing while reporting that it had. **And because it is a view, it is not persisted**: `state.VOLATILE_FILTERS` drops `trash` from the saved filter bar in *both* directions, so a settings file an older build wrote opens on the library too. Everything else in `Filters` narrows what you are looking at and is worth restoring; restoring this one reopens the app into a set that hides every asset, which is a setting nobody chose. The size/count figure the bulk bar draws beside **Empty trash...** is `service.jobs.trash_size`, measured through `ctx.submit` and drawn from the last answer -- the walk is the deferred-storage rule again, never the frame thread.

**The palette is two tables of one set of names, resolved live.** `tokens.PALETTES` holds dark and light and `theme.__getattr__` (PEP 562) resolves `theme.ACCENT` through whichever is in force -- which is why the switch needed no edit at any of the dozens of call sites, and why a module constant would have been wrong: it binds at import, so a switch would have repainted imgui's own style and left every hand-drawn rect, badge and ring on the old colours. `theme.apply` still has to be re-run, because imgui's style holds *copies*. The light palette keeps the elevation **roles** rather than inverting the numbers: PANEL is still the surface a form sits on and ELEV_1/ELEV_2 are still steps away from the floor, which on a light ground means darker. A stored theme name that this build does not carry falls back to dark rather than raising, because it comes out of a settings file. The font atlas is re-baked on a scale change **between frames** (`state.fonts_dirty` -> `fonts.reload`), never inside one: `clear_fonts` invalidates every `ImFont` handle and those are pushed and popped all through `_build_ui`. What actually needs the rebuild is `ICON_OFFSET`, baked as an absolute pixel figure at load time.

**Every animation in the app is a number `motion.py` owns, and reduce-motion is why that matters.** Nothing hand-rolls an easing any more: `motion.value` is the exponential approach for a value chasing a target that can change under it (hover, the sliding pill, the sidebar width), `motion.ease` is the one-shot ramp for a move with a known length (the mode veil, a popover's rise), and `ease_out_cubic`/`ease_in_out_cubic` are the curves -- the toast rise had its own written-out copy of the first of these, and a second spelling is precisely what the accessibility switch could not reach. `motion.REDUCED` collapses every duration in one place, so a consumer inherits it by reading from this module and by nothing else; under it a *fade* still runs where it is not movement (a toast's opacity, `drop_flash`'s acknowledgement keeps its dwell and loses its ramp) and `ease` reads 1.0 on its first frame -- **arrived, not never-appears**, which is the failure a naive `duration = 0` has. Three rules under that are load-bearing. `peek` reads without advancing, because a button's colour is needed to *draw* it and its hover is known only afterwards; calling `value` twice instead steps the easing twice a frame and towards the wrong target first, which is what made `card`'s lift take visibly longer to arrive than to leave. `animating()` is the idle clamp's fifth wake condition and counts only keys **the last frame touched** -- a card hovered and then navigated away from keeps a target nothing will ask for again, and without the frame stamp the app would never idle again either. And the one-frame lag in every hover is not a compromise but the only order available, which is why `note_hover` is a separate call after the item rather than a flag passed into it. `scripts/screenshot_modes.py` waits (bounded) on `animating()` before it reads a frame: three warm-up frames are 50 ms of a 200 ms transition, so without that every capture in the repo's own "somebody looked at it" pass is a picture of a half-cleared veil.

**Thirteen modes and one switch; 3D mode owns no prompt controls.** `studio/modes.py` is the whole list — `home`, `manual` | `2d`, `3d`, `inker`, `clay`, `poser`, `review`, `plotter`, `packwright` | `settings`, `library`, `profiles` — and it is *data only*: the dispatch stays hand-coded in `main._build_ui`, because "`state.mode` is the only thing that decides what a pane shows" is true only while there is exactly one place doing the deciding, and a table of callbacks would be a second. The switch is drawn in every mode (a mode that hides it is a dead end), and `AppState.mode` defaults to `"home"` — the app opens on Home every launch, which is what the deleted `state.landing` flag used to mean. **Library and Profiles are modes, and that is what let Home stop being a tile grid**: they were tiles behind a `state.landing_view` sub-view enum, which is what a real destination looks like when there is nowhere to put it, while the other seven tiles were the switch again under the same names and the same glyphs. Both are single panes drawing the call Home's tiles used to make, their two glyphs *moved* from `landing._SUBVIEW_ICONS` rather than re-picked, and `landing_view` is gone in both directions. No mode is persisted at all — a stored one would have no reader, and a write with no reader is how the halves drift, so `test_no_mode_is_persisted_anywhere` scans for `settings.set("mode", …)` and fails on any. `modes.WORK_MODES` (`2d`/`3d`/`inker`/`clay`/`poser`/`review`/`plotter`/`packwright`) is the subset that owns a viewport or a form and is therefore the only subset that takes keyboard shortcuts -- with one deliberate widening: Home's Resume list and the Library both take Up/Down/Enter for list navigation (a cursor over what is on screen, not a command about a pane that is not); `modes.VIEWPORT_MODES` (`2d`/`3d`) is the narrower one that draws the *asset* viewport and so the only one `_sync_viewer` acts for. Inker, Clay, Poser, Review, Plotter and Packwright are work modes that own their own centre pane — `modes.WORKSPACE_MODES` — which is why `_shortcut` returns after each one's `handle_key` **whether or not it consumed the key**: all six return False with nothing open, and the fall-through let F/W/S and Ctrl+Enter act on panes those modes have replaced. **There is no positional Alt+digit binding any more, and the removal is the decision rather than a casualty of one.** It was defensible while there were ten modes and ten digits, because the binding was then the picture on screen rather than a second table to keep in agreement with it. Thirteen segments against ten digits ends that: either two modes have no key, or something states which two — and that something is precisely the second table the positional scheme existed to avoid. So `mode_for_digit`/`digit_key_label`/`digit_for_mode` and `main._digit_keys` are **deleted rather than left unused** (a helper with no caller reads as a supported entry point — the `setup()` lesson), the digits go back to Clay's element modes and Review's grade scale, and `Ctrl+K` becomes the *only* keyboard route to a mode, which is what turns `palette._mode_commands`' derivation from `modes.MODES` from tidiness into a requirement. **The order is the grouping, and it is contiguous.** `GROUP_BREAKS` is derived from where the `WORK_MODES` predicate changes, never written out, and while the places were scattered — Settings eighth, between Review and Plotter, because it was appended when it was added and the positional digits were already in people's hands, with Plotter and Packwright then appended after *it* — that derivation honestly rendered four breaks. Nothing is typed positionally any more, so `MODES` was reordered to say what it means (the two ways in, then every workspace, then the three places about the program) and the derived set collapsed to the two real breaks **with nothing here to edit**: that is the whole payoff of deriving it, and a hand-written index would have gone on putting a gap in the middle of the workspaces until somebody noticed. **Thirteen segments also do not fit the resize floor at 1.5 UI scale**, and a clipped segment is an unreachable mode, so `widgets.segmented_control` takes a `compact` labelling (the glyph alone, full label in a tooltip) used when the full one exceeds `max_width` — **all-or-nothing**, because abbreviating only the segments that did not fit would be one control saying two kinds of thing, and which two would change as the window is dragged. Review is the one that *borrows* the shared asset viewer rather than drawing its own — for a bench run's `items/<unit>/model.glb` — which is exactly why it must stay out of `VIEWPORT_MODES`: `_sync_viewer` would otherwise reload the selected asset over the sweep unit on screen, and leaving the mode needs no cleanup because that same comparison against `viewer.path` reloads on the way back into 3D. **What decides whether Review loads is `viewer.path` too, never a remembered unit key**: unit keys repeat across runs of one sweep spec, so a key-keyed marker said "already showing that" about a *different run's* mesh and let a verdict be filed against something nobody had looked at — and it survived a trip through 3D, so coming back drew a library asset under Review's verdict buttons. `viewer.path` is set even when there is nothing to show, so an errored unit is attempted (and reported) once rather than every frame. `_review_viewport` also honours `viewer.pose_mode` exactly as `_sync_viewer` does, because loading over the pose editor discards unsaved rotations without the confirm `pose_panel.guard` puts in front of every other exit. Its state (`studio/review_mode.py`, the `clay_mode.py` shape: no imgui, `ctx.submit` for the bench-directory walk, `verdicts.record_verdict` inline on the frame thread) persists nothing at all, because a stored run directory outlives the sweep it names. Clay's viewport also takes the mouse in `_events` before the asset viewer sees it, or one drag orbits both. The Manual is a mode rather than a floating window, so `ManualState` carries no `open` flag at all; and the app-Settings pane (`panes/app_settings.py`) is the app's own settings rather than a job's — theme, layout, and what the app loaded. Its model list was read-only **by design** for as long as the app had no way to fetch anything, and that sentence is now retired: the rows carry a checkbox and a Download button (see the offline invariant's stated exception — the app still has no way to fetch anything, which is why the button spawns a child that does). What survives of the old rationale is the rest of the pane, which stays read-only where the answer is not the user's to change. Two things the button changed elsewhere. **Missing-ness is a flag, not a substring**: the rows used to be marked by testing a label for the literal word `"missing"`, which `main.py` only ever put into base-model labels — so every style LoRA was silently unmarked — and `service.downloads.rows` now carries a real `present` per row, from the same probes doctor reports. **And the pane's group headings are `fetch.KINDS`' own column, not a table beside it**: `_GROUPS` was a third hand-copy of the download-kind vocabulary (with `CHECK_PREFIXES` and `entries()`), under a comment claiming a new kind "cannot silently append unlabelled" — the exact opposite of what it did, since `_models` iterates the headings and so *dropped* an unlisted kind entirely. One `KINDS` table now owns the key, the registry it reads, doctor's row prefix and the pane's heading, and an unrecognised kind falls into an "Other" group rather than vanishing. And `Ctx.base_models`/`style_loras`/`model_rows` are **no longer immutable**: they were documented as read-once-at-startup, which was true only while nothing could make weights appear, so a finished fetch re-runs `doctor.run_checks` wholesale (`current_checks(force=True)`, past the health TTL, because the disk demonstrably just changed) and recomputes all three. The two generate modes share the settings / viewport / selected-asset-inspector three-column layout; everything in `main._SINGLE_PANE_MODES` (`home`, `manual`, `settings`, `library`, `profiles`) fills the host window with one pane; `WORKSPACE_MODES` fills it with a mode's own three-column workspace; and those three sets must partition `modes.KEYS` exactly — the dispatch ends in a bare `else` that would otherwise draw Inker for an unlisted mode. It is the two-stage pipeline that already existed made visible: 2D always submits `output=reference` and owns every field that composes the SDXL prompt; 3D starts from a finished 2D asset (`service.jobs.promote_to_model`, whose mesh-side params are all optional overrides) or an upload, and owns only mesh, rig, pose and sheet controls. A control belongs to exactly one pane — `platform` is the one field both need and it is deliberately *two* selects, the 2D pane's (a prompt fragment) and the 3D pane's (the geometry resolution), because one control cannot be owned by two panes. Plotter and Packwright follow the same rule inside their own workspaces: the tileset pane is the sole owner of what a stamp puts down, the layers pane of object metadata, and `packwright_settings` of `PackSettings` — every write to which goes through `packwright_mode.set_settings`, the one place that both pushes the undo step and marks the pack dirty. Anything the worker records about a finished job's artifacts still has to join `service.validation.DERIVED_PARAMS`, or an override-carrying promotion inherits a verdict about a mesh that doesn't exist.

**Home answers three questions, and none of them is "where do I go".** The first-run orientation card is gone with the grid it explained: a card telling you which pipeline to start in sat above a screen whose whole left column is now a status report and whose right column is a list of what you were doing, and an explanation of a screen that explains itself is one more thing to dismiss. It was a grid of nine 380x64 tiles, seven of which were `modes.MODES` again — the same names under the same glyphs, one click either way, against a switch that is drawn unconditionally at the top of *every* frame. So the screen the app opens on spent all of itself re-offering navigation that is permanently on screen. It is two columns now: what changed and what the machine is doing on one side, what you were working on down the other. Four rules under that. **The changelog is hand-written and only read** (`CHANGELOG.md` at the repo root, force-included into the wheel exactly as `docs/manual` is, parsed by the stdlib-only `warlock/changelog.py` which answers `[]` for every way of having nothing to say): every commit subject in this repository is `Warlock vN.N.N` and carries no detail, so a generated changelog would be a column of version numbers — and `tests/test_changelog.py` pins the top heading against `pyproject.toml`, because a hand-written file is exactly what a release bump leaves behind. **The Resume list is one list, which is why `studio/recents.py` had to exist**: Inker, Clay, Plotter and Packwright each kept their own `recent: list[str]`, and merging four bare path lists at draw time is not untidy but *impossible* — they carry an order within themselves and none between them — so the four fields and their eight near-identical `remember`/`forget` methods are gone, replaced by one timestamped list with a one-shot migration off the four legacy settings keys (which are left in place, so an older build still reads them; a `None` stamp sorts last, `Filters.order`'s rule for an unanswerable row). **Assets get no write path at all**: a job row already has a `created_at`, so Home derives those rows from the cache at draw time, and a row that is trashed or pruned simply stops being an answer with nothing to clean up. And **the status block's unreviewed count is asked for on a cadence, never on the frame thread** — it is a table scan behind the one serialized connection — with the stamp moved only when `ctx.submit` *accepted* the request, the `findings_dirty` rule, or a refusal strands the row on a figure nothing will recompute; `None` (not asked) and `0` (nothing waiting) both draw as no row, because "0 unreviewed" is a claim about an install nobody has measured.

**Plotter is a mode, and its engine is pure.** `studio/plotter/` is the fourth headless package beside `inker/`, `clay/` and `packwright/` — stdlib, numpy, a lazy Pillow, and `studio.undo`, pinned exactly by `tests/plotter/test_plotter_imports.py`. **A cell is one `uint32` and the three transform flags travel through every hop bit-exactly**: `FLIP_H` is `0x80000000`, so an `int32` layer would store it as a negative number and every comparison after that is an argument about two's complement. Nothing between the reader and the renderer re-derives them, which is what makes `tools.flood_fill` match on the *full encoded value* — a mirrored wall tile bounds a fill of its unmirrored twin, which is the right answer because two cells that draw differently are two different cells. **A Tiled feature this editor does not model is refused by name, never dropped** -- and a refusal only ever moves because the editor learned to model the thing: isometric left the list when `plotter/project.py` arrived and `tests/plotter/test_tmx_refusals.py` gained the acceptance case in the same change, while staggered and hexagonal stayed, which is also what keeps `gid`'s missing hexagonal-rotation bit honest (a file that could set one never gets past the door, and `tmx._finish` now probes for it *by name* rather than letting it fail as an out-of-range id, which is how it was caught before -- the right outcome under the wrong sentence). Tiled's Wang sets are **recognise-or-refuse** rather than refused outright, and the asymmetry is the point: what is recognised is exactly what `tsx.write_wangsets` emits, so the reader and the writer stay symmetric and a generated atlas opens in Tiled with a working terrain brush, while any *foreign* Wang set -- corner-only, 255 colours, tiles that form no blob -- is still named and refused, because adopting one would be the silent half-read the whole rule exists to prevent. The refusals are: the drop is invisible right up to the moment the user saves, at which point the other half is gone, and `tests/plotter/test_tmx_refusals.py` has one case per entry. Rotated objects are refused (an unrotated outline drawn for a rotated object is a *wrong picture*, and a wrong picture is worse than a refusal) while hidden ones are modelled (hiding changes nothing about where a thing is). **`.wmap` stores indices, never uids**, which is why it needs no `reserve_uid` where `.wblk` does: nothing is ever restored onto a number the counter has already issued. Two renderers exist and neither is redundant — `panes/plotter_canvas` issues one `add_image_quad` per *visible* cell (a 200×200 map at 32px is a 40-megapixel buffer; recompositing it per frame is not frame-thread work) and `plotter/render.py` composites the whole map for an export. They agree because both take orientation from `gid` and placement from `tile_rect`, and both apply the flags **transpose-then-mirror**; the quad form is what makes the diagonal flip drawable at all, since a transpose cannot be expressed by swapping a UV pair but can by permuting four corners. **A map's projection is a document property and one function owns it.** `plotter/project.py` maps a cell to a pixel rect and back for both lattices, and `MapDoc` defers to it, so `panes/plotter_canvas` and `plotter/render.py` take placement from one answer for the same reason they both take orientation from `gid`. A ground tile's image is the diamond's *bounding rect*, so the drawn quad stays axis-aligned in pixel space and the transpose-then-mirror permutation is untouched -- isometric is a change of placement, not of rasterisation, which is why both lattices shipped together rather than the second being a rewrite. The inverse is exact rather than a hit test: the diamond lattice is the image of the square lattice under an affine map, so flooring the transformed point **is** the cell, and a click on a shared corner lands in exactly one of them. Draw order is `column + row` ascending for isometric and row-major for orthogonal, because row-major is not monotone in isometric screen depth -- cell `(width - 1, 0)` sits in front of `(0, 1)` -- which is invisible for flat ground tiles and correct on the day something overhangs. Tiled measures an isometric *object* in tile-space units of the tile height rather than in the projected plane, so `project.object_to_pixels` converts in both directions: a spawn point that made the trip untouched would reopen somewhere else and say nothing about it. **A terrain is derived from the gid, never stored beside it.** A parallel per-cell terrain array would be a second source of truth that `.wmap`, the undo stack and every Tiled round trip would each have to keep honest; a 47-case blob set makes the tile id answer alone (`Tileset.terrain_of` is `local // 47`), so a terrain stroke is nothing but a `TilePatchEdit` and a cell hand-stamped with the plain stamp tool joins the field for free. **Precedence is list position and membership is "ranked at or above me"**, which is what makes a three-terrain junction resolve to one tile per cell with the outline always belonging to the higher-precedence terrain; the cost, stated in `terrain.py` so nobody quietly "fixes" it, is that a terrain's edge art cannot vary by what is on the other side. **And a stroke is one step.** `MapDoc.begin_stroke`/`stroke_write`/`end_stroke` is `inker.Document`'s stroke session over gids -- the live array is written with no history and one patch over the dirty box is pushed at release -- because `_apply` runs every frame the button is down, so a stamp dragged across forty cells used to push forty steps and forty entries against the byte budget. It is a second write door into a layer, which is why `end_stroke` is idempotent and the canvas closes any open session on the first frame the mouse is not down: a session left open is a document whose cells are ahead of its head.

**Packwright's packer is deterministic, and that is a contract rather than an accident.** `studio/packwright/` reaches outward exactly four times — `layout.py` → `pipelines.sheet`, `tsxout.py` → `plotter.tsx` **and** `plotter.tileset`, `document.py` → `studio.undo` — and every one is the same argument: reach for the module that *owns* a definition rather than restating it. `pipelines.sheet` owns the atlas ceiling (and `trim.py` is pinned against `measure_trim` by a parity test, which is the whole licence for a second implementation existing), `plotter.tsx` owns the `.tsx` format with `plotter.tileset` owning the `Tileset` that format is written from, and `studio.undo` owns history. **`inker` is deliberately not among them**: `sources.py` takes *a document* and asks it for frames rather than importing the package, because a packer is routinely handed loose PNGs and no document at all. `tests/packwright/test_packwright_imports.py` pins the set of four exactly, which is the `tests/inker/test_sheetout.py` idiom's third instance. Determinism rests on three things and all three are load-bearing: a canonical input order (`maxrects.order`), positional tie-breaks in the free-rectangle scoring, and **no set or dict iteration anywhere in `maxrects`** — asserted by parsing the module, because iteration order over either is stable until the day it is not. **The layout is derived, never stored**, which is what makes a re-export of an unchanged document byte-identical with nothing to invalidate. `padding >= extrude * 2` is validated in `PackSettings` because two neighbours extrude into one gutter, and the whole pack is offset by one `padding` so a sprite has room on all four sides *including against the atlas edge* — the case an un-offset MaxRects pack gets wrong, which here is an out-of-bounds write rather than a cosmetic artefact. **A repack is a task re-armed by a flag** (`PackTab.pack_dirty`, pumped from the preview pane's draw and cleared *only when the submit is accepted*): the `findings_dirty` lesson verbatim, because `TaskRunner.submit` refuses a key already in flight and nothing else re-arms it. And **the sidecar is TexturePacker's schema, deliberately not `pipelines.sheet.sidecar`** — that format is Warlock's own, versioned, with one writer, and a second one is how `version: 1` comes to mean two documents.

**An exported map or atlas is an ordinary asset, and `params["authored"]` is what makes it reopenable.** `map.wmap` and `pack.wpack` follow the `paint.ora`/`build.wblk` precedent exactly: absent from `MEDIA` and `LISTED`, never served, gone with the job directory for free, and with no staleness rule (nothing rewrites one behind its document). The marker on the row is the part that is new and it exists for a specific reason: reopening has **no fallback**, unlike *Edit in Clay*, which imports `model.glb` when there is no `.wblk` — so the library has to know whether the source is there *before* offering the menu item, and it must answer from the cached row rather than a stat because the menu is built on the frame thread. `authored` is an *input*, like `built`, so it stays out of `DERIVED_PARAMS`.

**The sidebars are one of three named widths — never dragged — and the padding is pushed per pane.** `layout.SIDEBAR_WIDTHS` is the table (`narrow` 260, `default` 300, `wide` 360 design px; M106) and `layout.SIDEBAR_W` is the one in force — module state set by `layout.set_sidebar`, exactly as `tokens.SCALE` is, because eight call sites read it directly and threading a `Layout` through all of them would put the measurement in eight places instead of one. An unknown stored key falls back to `default` rather than raising, since it comes out of a settings file. A *change* to it eases (UX.md Phase 1), which is why `set_sidebar` takes `animate` and why `layout.tick()` is called **once, before any pane reads the width**: the construction path and every headless caller need `SIDEBAR_W` correct with no frame loop at all, so they snap, while the Settings option seeds the motion key and lets the tick slide it — and a half-eased width read by the left column against a settled one read by the right would be two columns disagreeing about the same frame. `layout.SIDEBAR_W` is the width every left and right pane takes and `layout.centre_width()` is what the centre reserves for the right one; a *draggable* splitter is refused by `layout.py`'s own header, so the only proportion the user still drags is `settings_share`, the sidebar's internal horizontal split, and `Layout.save` writes exactly the two surviving keys (`settings_share` and `sidebar`, the width's *name* rather than a number, so a stored value can never be a size this build does not offer) — `Settings.set` replaces the whole dict, so the stale `sidebar_w`/`inspector_w` a settings file still carries die on the first save rather than being half-honoured. Every pane goes through `layout.pane_child`, which pushes `window_padding` around `begin_child` **and pops it immediately after** — window padding latches at begin, so this scopes it to the pane while a popup or tooltip opened inside keeps the theme's own. Pushing 5 px globally in `theme.py` instead would shrink every modal in the app.

**Inker is a mode, not a takeover, and its engine is pure.** `studio/inker/` is a layered raster editor -- blend arithmetic, canvas-sized layers with stable uids, typed undo edits, 8-bit selection masks, a cached brush stamp, gradients, geometry, OpenRaster I/O -- and nothing under it may import imgui, moderngl, pygame or `service`, which is what makes every rule about pixels assertable headlessly. **Undo is dirty-rect patches addressed by layer uid**, never by index, so an undo issued after a reorder still lands on the layer the edit was made to; only whole-canvas geometry copies, and it redoes by *replaying* rather than storing a second copy. Three consequences of addressing by uid are load-bearing and each was once wrong. A snapshot restore (`restore_snapshot`, `_replay`) copies pixels but **keeps the uids** -- an undo restores the document's state, not a set of new layers, and minting fresh ones strands every patch recorded beneath it. A replayed op that *creates* a layer (`flatten_layers`) draws its uid once via `layers.new_uid` and closes over it, because replay must be a pure function of the document and minting is the one part that is not. And a patch can land *below* the active layer, so `Document.invalidate` takes the written layer's uid and repairs the cached `_below` composite over the same rectangle -- otherwise the pixels change and the composite, the flatten and every save derived from it keep showing the old ones. Patches also own their pixels: `PatchEdit` copies any array that is a view, because a slice of a full-canvas buffer reports its own tiny `nbytes` while keeping the whole base alive, and that number is what eviction is driven by. **Dirty is a comparison against `history.head`, not a flag** -- `Document.rev` counts changes and an undo is a change, so a rev-based check would call an undone document unsaved forever. And **the eraser cuts alpha**: the old `erase_color` became `Document.matte`, applied once at flatten, so what a photo exports onto is a property of the document rather than of every stroke. **A floating buffer holds the history entry it owns**, not a flag saying it owns one (`FloatingBuffer.lift_edit`, with `.lifted` derived from it): a lift cut a hole and pushed a patch, a paste took clipboard pixels and touched no layer. Cancelling reverses *that* entry, via `UndoStack.revoke`, and never simply "the newest step" -- a buffer floats for as long as the user leaves it floating and every selection op pushes a step meanwhile, so the lift is routinely no longer on top, and reversing the top instead dropped the lifted pixels, kept the alpha-cut and destroyed an unrelated edit. Revoking out of order is sound only because everything that writes pixels calls `commit_floating` first, so nothing above the lift describes the region it restores. It is reversed *unredoably*, because the user asked for the lift not to have happened and leaving it on the redo stack lets Ctrl+Y replay the alpha-cut with no buffer left to restore. `Document.undo` returns as soon as it cancels, since the cancel *is* the step; `paste` clears the redo branch itself, having pushed nothing that would. **A step that changes nothing is not pushed**: `select` returns early when before and after are both `None` (subtracting from an empty selection) *and* when they are equal non-empty masks (a marquee redrawn over itself, Select All twice, feather 0), because dirty is a comparison against the head and a no-op step made a saved document ask to be saved again. `LayerStack.remove` **shifts** `active_index` for a removal below it rather than only clamping it, or the active layer silently becomes a different layer; and `LayerAddEdit` reports its layer's `nbytes` as its cost, because an undone add holds the only reference to a full-canvas buffer and a zero cost hid it from the byte budget entirely.

**The canvas view turns in quarter turns, and that is the decision rather than a first instalment.** `inker_state.ROTATIONS` is `(0, 90, 180, 270)` with `flipped` beside it, both on `PaintView` and neither ever reaching a pixel — there is nothing to undo and nothing to save. The narrowing is what keeps the pane's overlays as they were: a free angle makes the grid stop being two families of axis-aligned lines, the marquee preview stop being a rect and the transform box's handles stop being squares, and a half-done version silently misplaces all of them, which is worse than not having it. A **quarter** turn maps an axis-aligned image rectangle onto an axis-aligned *screen* rectangle, so `_box` (min/max of the four transformed corners) is exact rather than conservative and every `add_rect` in the pane is still drawing the shape it names. Three rules follow. `inker_state.basis` is the orientation alone, **separate from the zoom and orthonormal**, which is why `ants.dash_segments` needed one optional matmul in `_points_at` and no change to any of its arithmetic — every distance in it is an arc length in canvas space and turning does not stretch. `to_image` inverts the basis by **transposing** it, exact for all eight orientations. And every image goes through `_blit`/`add_image_quad` rather than `add_image`, whose two-corner form can only draw an upright rectangle; the checkerboard is the one deliberate exception, drawn upright in screen space because it is the surface the page sits on rather than part of the page. The failure this invites is not a crash but one overlay left computing `origin + x * zoom` for itself — right at rotation 0 and a quarter turn out everywhere else — which is why `_grid` derives its visible index range by inverse-transforming the window's corners instead of dividing a screen offset by the zoom, and why the ants' loop-box cull transforms its four corners rather than scaling the box.

`studio/inker_mode.py` is the only layer that knows about jobs and task threads: no dialog and no encode ever runs on the frame thread, which is why saving is a state (`InkerDoc.saving`) rather than a call that returns, and why a failed save has to clear it (`on_task_failed`) or the tab stays read-only. Two rules follow from `saving` being that state. **Every save commits the floating buffer first, and reads `history.head` after** -- the encoders walk the layer stack and a floating buffer is in no layer, so an uncommitted paste was written to no file while `mark_saved` called the document clean; and the commit pushes a step, so a head captured before it saves the document against a head one behind, leaving the tab dirty however many times it is saved. **And every control that changes the document is gated on `saving`** -- the canvas, the keyboard path (`_MUTATING_CTRL`), the layers panel, `inker_bridge`'s canvas ops and resize popup, and `inker_tools`' selection and transform sections. `write_ora` flattens, writes `stack.xml`, then walks the stack writing one PNG per layer, so a rotate or an undo landing mid-write produces an archive whose parts disagree about the canvas size. A stroke is the deliberate exception: pixels are written in place, so the worst case is a file catching a stroke mid-flight. That gate is now `InkerDoc.busy`, not `saving`: **playback is the second reason the document may not be restructured**, and it is the same list of controls for the same reason, so it is one question asked once rather than two flags nine panes have to remember to `or` together.

**An animated document is a sparse grid, and `Document.anim is None` is exactly the editor that existed before it.** `studio/inker/animation.py` holds `Track` (a *layer's identity* — name, opacity, visibility, blend, once) x `Frame` (a duration, and nothing else) with `cels: dict[(track_uid, frame_uid), Layer]`, and `Document._materialize_frame` rebuilds `stack` as the current frame's view — so the panes, the tools, the floating buffer, the selection, the `_below` cache and the compositor all go on seeing an ordinary `LayerStack`, because that is genuinely what they are handed. Properties live on the track because storing them per cel makes hiding a layer an edit to every frame it appears in, and a frame with no cel has nowhere to put the answer at all. Six rules under that are load-bearing. **A link is two slots holding one object** — there is no link table and no "linked to" field, so an edit to a linked cel shows on every frame it occupies with no propagation step that could be forgotten; the price is that every whole-grid walk must go through `Animation.unique_cel_layers()`, or a rotate turns a three-frame background three times and every frame agrees with every other about the wrong answer. **An absent cel is an absent key**, and materialising fills the gaps with placeholders sharing one *read-only* transparent plane: shared because ten tracks over twenty empty frames at 2048 square is 3.2 GiB of nothing, read-only because sharing is only safe while nothing writes and a stray write would otherwise appear in every empty cel at once with nothing to say where it came from. So **every write path calls `_ensure_cel_for` first** (keyed by uid, not "the active layer", because committing a floating buffer writes to whichever layer it was lifted from), the autovivified cel rides into the *same* `CompoundEdit` as the patch, and a write that changes nothing takes the cel back out and pushes nothing — the "a step that changes nothing is not pushed" rule, extended one level. **The playhead is view state**: `set_current_frame` mirrors `set_active_layer` exactly and pushes no step, or a document asks to be saved because the user looked at another frame. **`invalidate_all` stamps no frame** — it is about the composite on screen and most of what reaches it changes no pixels, so stamping there looked conservative and was the opposite of a cache: every step of the playhead threw away every frame's flatten and onion skinning recomposited its neighbours on every keypress. The callers that really do change every frame (`_anim_changed`, `apply_matte`, `_map_planes`, `restore_snapshot`) say so with `_stamp_all`. And **`ReplayEdit` carries the grid as slot *indices* into its snapshot list**, so an undo of a rotate gives back one shared object where the document had one — restoring per slot yields two equal copies and silently breaks the link, which only shows on the next stroke when one frame changes and the other does not. A snapshot whose animated-ness disagrees with the document's is **refused** rather than flattened, in both directions and before anything is mutated: history is LIFO, so a document de-animated after the step was pushed is a state nothing can legitimately reach, and silently dropping the grid to restore the pixels would lose a whole timeline to paper over a bug somewhere else. `merge_down`/`flatten_layers` are refused outright while animated (`Document.can_restructure`): both are defined over one stack and an animated document has one per frame. Two more callers had to learn `unique_cel_layers`'s rule the hard way and are named here so a third does not. **`duplicate_layer` copies once per distinct cel**, not once per slot — per slot gave the duplicate three independent frames where the original had one shared one, the link silently gone and three times the pixels, and it only shows on the next stroke. And **`apply_matte` walks the grid, not the current frame's stack**: a cutout describes the drawing rather than a moment of it, so mattes applied to one frame while `_stamp_all` announced that every frame had changed was the worst of both. The byte budget learned the same lesson from the other side — `anim_edits.charged` takes the `id()`s of the cels a removal actually *released*, because a frame routinely holds one cel the grid is letting go of beside another still linked into the frame next door, and a bool is wrong whichever way it is set. Tags are the one part of the grid that is not addressed by uid: a tag's identity is its position, so `TagsEdit` snapshots the whole list (a name and three numbers, and no pixels, so it costs the budget nothing) and one type covers create, rename, retime, loop and delete.

**`animation.json` is the record; the frame groups in `stack.xml` are the picture.** An animated `.ora` gains one member carrying the grid — durations, track properties, which slots hold which cel and which slots share one — and `stack.xml` becomes an interop *projection* of it, one nested `<stack name="frame:NNNN">` per frame with frames 2+ written `visibility="hidden"` on the group **and** on every layer inside it, so Krita, GIMP and this reader's own flattening fallback show frame 1 rather than the whole clip stacked on itself. The two cannot be derived from each other (XML has nowhere to put a duration and no way to say "these two entries are the same cel, not two equal ones"), so one is authoritative rather than the truth being split. The JSON stores **indices, not uids** — uids are minted per process and mean nothing in a file — and a linked cel is one `data/cel{n}.png` referenced by several slots, decoded once on read and *shared*, which is the whole of how a link survives a round trip. Any way `animation.json` fails to make sense on its own terms — a version it was not written against, an index outside the grid it declares, a cel naming a PNG the archive does not hold — logs and falls back to the flat read, and it fails the **whole** grid rather than skipping a bad cel: half a timeline is harder to notice than none of one. It deliberately does *not* cross-check the JSON against `stack.xml`: the XML is the projection, so a disagreement is the picture being wrong about a document the record describes correctly, and throwing the grid away over it would lose the animation to fix the picture of it. A frame entry with no `duration_ms` gets `DEFAULT_DURATION_MS`, not `clamp_duration`'s 1 ms floor — a clip a hundred times too fast still plays, which is exactly why the floor was the wrong fallback. The accepted, unrecoverable cost is that an older build opens such a file, sees frame 1, and writes it back flat. **Every member carries a fixed `_EPOCH` stamp**, so `.ora` joins `.wblk`/`.wmap`/`.wpack` as byte-reproducible and two saves of an unchanged document are identical — it was the odd one out, stamping every member but `mimetype` from the wall clock. That one member had always carried this exact stamp (a bare `ZipInfo`'s default) and is the first thing every ORA reader touches, which is the evidence the format tolerates it; `_member` restates `ZIP_DEFLATED` and `external_attr` because `writestr` takes those off a supplied `ZipInfo` rather than from the archive.

**Indexed colour is a constraint on writes, not an index plane, and `_commit_patch` is where it is applied.** `Document.palette` is a list of RGBA or `None`, and present means every write snaps onto it. There is deliberately no palette-index storage: `Layer.__post_init__` hard-enforces `(H, W, 4)` uint8 and every blend mode, brush coverage accumulation, filter, selection mask and native kernel in the package is written against RGBA, so an index plane would be a rewrite of `studio/inker/` for nothing a user can see -- what the mode is *for* (no stray near-colours, a palette-wide recolour that reaches every pixel, an export whose colour table is the authored one) falls out of carrying a table and snapping to it. `studio/inker/indexed.py` is the whole of the arithmetic, pure numpy, and it snaps in **straight** (non-premultiplied) RGB for `transform._resample`'s reason -- premultiplying drags every partially transparent pixel towards black, so a soft white edge would land on the dark swatch. **Alpha is never snapped and a fully transparent pixel is never touched**: a palette constrains colour and not opacity, so a soft nib is still legal and simply bands; and rewriting a transparent pixel's dead RGB would make a no-op write look like an edit to `_commit_patch` and push an undo step for a gesture that changed nothing. The snap goes in `_commit_patch` rather than in each tool because every undoable write arrives there -- strokes, fills, shapes, gradients, filters, pastes, floating commits -- and it happens *before* `after` is read, so the recorded step is the pixels the document ends up with and undo-then-redo is stable. The palette *edits* (adopt, recolour a slot, delete a slot merging into the nearest survivor) are whole-document rewrites and go through `_replay`/`_map_planes` like a rotate: that is what makes each one **one** undo step across every layer and every frame, and it inherits `unique_cel_layers`'s rule for free. `snap` works over a region's *distinct* colours via a packed `np.unique` rather than over its pixels, which is what keeps a 40-frame 2048-square clip inside a frame -- and pixel art is the case where that wins by the most. Persistence is additive and versionless: a `palette.gpl` member in the `.ora` (`gpl.py` already reads and writes the one interchange format for a row of swatches), and a reader that does not know about it opens the file as the ordinary RGBA document the pixels already are; a palette member that will not parse costs the *constraint*, never the file. The GIF exporter takes the table verbatim when it has one -- slot *n* is the same colour in every frame, which is exactly what the adaptive per-frame quantise cannot promise -- and falls back to quantising rather than truncating a palette too long for the format, because a dropped swatch is pixels changing colour in the export. **The session swatch row is a different thing and stays one**: it is persisted in settings, it belongs to no file, and adding to it changes no pixel.

**Frames are cached by their own stamp, and the cache is LRU where the history is not.** `Document.frame_flat` is what onion skinning asks for two or four of per drawn frame and playback one of per tick, so it is a lookup; it is keyed on `_frame_stamps[frame_uid]` rather than on `rev`, because `rev` moves for any change anywhere. Eviction is least-recently-used and bounded by `FRAME_CACHE_BYTES` — deliberately *not* `UndoStack`'s oldest-first policy, which keeps the newest steps because that is what history means, and which here would evict the frame a playback loop is about to come round to. The entry just stored is never evicted, or a canvas larger than the budget caches nothing and recomposites on every draw. `panes/inker_textures.frame_texture` sits inside the existing `inker_tex:{uid}:` naming so `release_doc`'s prefix sweep collects a fifty-frame tab's textures without knowing they exist.

**Playback ticks from the timeline pane's `draw`, and it never moves the document.** There is no per-mode update hook, so the pane is the only thing that runs every frame — the `motion.py` idiom — and it calls one function in `inker_mode` whose arithmetic is the pure `animation.advance`. `tick_playback` deliberately does not call `set_current_frame`: that re-materialises the stack and recomposites the whole canvas sixty times a second to show a picture the frame cache already has, so `play_index` lives on the tab and the canvas draws that frame's cached flatten, with stopping the one moment the document catches up. `advance` accumulates time rather than deriving an index from a clock, because a duration is per frame and a clip is therefore not a rate; it steps in a **`while`**, or a 200 ms hitch behind 10 ms frames runs the clip at a twentieth speed whenever the machine is busy; and the caller clamps `dt` to `MAX_TICK_MS`, or a two-second stall fast-forwards through twenty frames at once.

**An Inker clip exports through `pipelines/sheet.py`, which is why that module grew non-square cells.** `Plan.frame_w`/`frame_h` default to 0 meaning "square, i.e. `frame_size`", `cell_w`/`cell_h` are what `width`/`height`/`pack`/`sidecar` now read, and `Cell.as_dict(w, h=None)` defaults `h` to `w` — so every 3D sheet takes character-for-character the arithmetic it always did, pinned by a **byte-identical `json.dumps` of a square sidecar** captured before the change (one string equality covers values, key order and the absence of any new key, which a field-by-field check would miss). A non-square sidecar emits `frame_size: 0` and carries `frame_w`/`frame_h`: zero is a loud wrong answer, where putting the width in `frame_size` would let an importer that reads only that key slice the atlas correctly across and wrongly down. `studio/inker/sheetout.py` builds the cells itself — `plan()`'s job is poses by yaws and its `FRAME_SIZES` check refuses a canvas outright — but emits through `sidecar`, because a second writer of a versioned public format is how `version: 1` comes to mean two subtly different documents. Row wrapping is required rather than tidy (32 frames of a 320px canvas is 10240px across), which is why `check_atlas_size` was extracted from `plan` rather than approximated. The export is split at `snapshot`/`compose` and the split is a thread boundary, not tidiness: `_write` gets away with encoding the live document because the encoders only read, and flattening a clip does not — `frame_flat` fills and evicts the frame cache and `layers_for` copies track properties down onto cels, which is what the onion-skin draw is doing to the same dicts. So `snapshot` runs on the frame thread at click time and `compose` takes no document at all. **It is the first module under `studio/inker/` to import outside the package**, and `tests/inker/test_sheetout.py` pins the whole outward set exactly, so the next one is a decision rather than a discovery; the invariant is about staying assertable headlessly, and `sheet` is stdlib plus a lazy Pillow import, while the inverse placement would make `pipelines` — which runs inside worker and Blender processes — depend on `studio`.

**A mesh is an immutable CSR array, and the frozen dataclass is a cache key.** `studio/clay/mesh.py` stores a mesh the way a sparse matrix is stored — one flat `loops` array of face corners and a `starts` array of offsets, so face *i* is `loops[starts[i]:starts[i+1]]` — because an n-gon then needs no triangulation to be *stored* (a cylinder cap is one face the user can select, not thirty fans) and Phase 2's extrude and inset append rather than rebuild. Triangulation is a *rendering* concern, produced by `triangulate` on the way to the GPU and never written back. Every array is copied on construction and made read-only, and every op is `Mesh -> Mesh`. That immutability is load-bearing three times over: an undo step that owns its arrays reports its true `nbytes` to eviction (a view of a shared vertex buffer reports its own tiny size while pinning the whole base alive); a snapshot undo is affordable because the "before" mesh *is* the object the document was holding; and `studio/clay_view.py`'s GPU cache keys on `id(obj.mesh)`, so an in-place mutation anywhere would leave the cache holding a live key over stale geometry and the viewport would render the old shape forever with nothing in the data to say why. The transform is deliberately **not** in that key — it is a uniform, so moving an object must rebuild nothing. `edges`, `_next_corner` and `_face_normals` assume an already-validated mesh and go *quietly* wrong rather than raising on a short face, which is why `serialize.read_wblk` validates rather than trusts.

**One conversion out, three consumers.** `clay/document.to_model` is the only thing that turns a `ClayDoc` into a `viewer.gltf.Model`, and the viewport, `viewer/glbwrite.write_glb` and the flat render handed to trellis all go through it — so "what does this document look like" has exactly one answer and those three can never disagree. A hidden object is simply not in the model: `visible=False` means it does not render, does not export and cannot be picked, and one flag enforcing all three in one place is the only way those three stay true together (`clay_view` releases a hidden object's GPU buffers for the same reason). Materials are `viewer.gltf.Material` objects rather than a parallel Clay type — they are already pure data, and `GpuMaterial`, `to_model` and `write_glb` all de-duplicate on `id(material)`, which is why every edit to a palette entry writes a *replacement* and never mutates one in place. `write_glb` refuses a skin rather than dropping it, and omits the buffer entirely for an empty document, because `byteLength` has a minimum of one in the spec.

**Clay's undo is uid-addressed, and its selection is deliberately not undoable.** `studio/undo.py` is the engine the raster editor and Clay share — it was extracted out of `inker/undo.py` for exactly this, and neither half knows what the other edits. Every edit in `clay/edits.py` names its object by uid, never by index, so an undo issued after an outliner reorder still lands on the object the edit was made to; `ObjectAddEdit`/`ObjectRemoveEdit` hold the `Obj` itself rather than a copy, so re-insertion keeps the uid a mesh edit recorded earlier still names. Selection pushes no step at all: clicking an object is not laborious to redo the way a lasso is, and an undoable selection would move `history.head` and make a document ask to be saved because the user looked at something else — which is what keeps `dirty == history.head != saved_head` honest. `document.reserve_uid` exists because the counter is per *process*: a `.wblk` whose uids run past this session's would otherwise collide with the next new object. A gizmo drag applies in place and commits **one** step per object on release, against the transforms recorded at the press — which is what `set_transform`'s `was` argument is for, and why a gizmo must rebind rather than write through `trs()`'s live arrays.

**Geometry that is no longer what a generator would build freezes it, and `Document.set_mesh` is where that happens.** Not the op layer, which is where it was and where it was only half applied: `clay_ops.run_mesh_op` and Smooth cleared `generator`, while Delete, Bake Transform, Mirror and an element drag went straight to `set_mesh` and kept it — so the object still claimed to be "box, size 1", the properties panel kept offering that size field, and touching it called `build(**edited)` and replaced the mesh with a pristine box. The edit was gone with no warning. The freeze is pushed *with* the mesh edit as one `CompoundEdit`, so it undoes with the edit it belongs to — it used to be a second step, and one Ctrl+Z then restored the generator claim over the still-edited mesh, the exact state the freeze exists to prevent — and `keep_generator=True` is the single exception: `panes/clay_props.py`'s own rebuild, where the new mesh *is* what the generator makes and the claim is still true.

**A drag delta is narrowed in one place, and an explicit constraint beats a snap.** `clay/drag.py` is pure in the `vram.py` sense (numpy plus `viewer.math3d` for the one quaternion, nothing from `service`/`queue`/`studio`) and is a *filter*: every function is `(quantity, lock) -> quantity`, so the three gizmos, the element-drag preview and the commit all go on knowing only that they were handed a delta. `ClayView._narrow` is the single place it is applied, above both the object path and the element path, which is also what fixes the order — a user who has typed `X 2` has said exactly where the thing goes, so a nearby vertex must not quietly overrule it, and `_element_world_transform`/`_apply` stand the grid down for either. **A typed value replaces the quantity; an axis lock only projects it**, which is why a number with no lock is still meaningful (it sets the length of the displacement the mouse chose the direction of) and why a locked scale returns the *other* axes to one rather than leaving them dragged. `ClayView.dragging` is checked before every other binding in `clay_mode.handle_key`, because the number row is bound to the element modes and a `1` typed into a drag must be a digit; Esc there is `cancel_drag`, which puts the transforms back and records nothing — it used to clear the pane's bookkeeping and leave the view holding the grab, so the objects stayed where the last motion put them with no step to undo. Proportional editing is one weight per vertex and nothing else (`falloff` is `1 - smoothstep`, because a linear ramp creases at both the selection boundary and the radius, which is the ridge the feature exists to avoid), the radius is world metres divided by the object's largest scale component (`ops.join`'s rule), and the neighbourhood is measured **from the nearest selected vertex** rather than from a centroid the geometry may not pass through. Snapping is screen-space through `pick.nearest_vertex`'s new `allowed` mask, which exists for one reason: a drag that could snap onto its own moving geometry would track the cursor exactly and report a snap, which looks like the feature working.

**The two boundary ops rest on one fact: a `Mesh` stores no wire edges.** `edges` is derived from face corners, so an edge exists exactly while some face uses it — which is why `ops_topo.extrude_edges` and `bridge_edges` refuse an interior edge by name rather than guessing, and why **a vertex extrude is not implementable at all**: an extruded lone vertex is a position no face uses, which `compact_vertices` drops on the way out. `extrude_verts` therefore extrudes the *border* edges a vertex selection implies and refuses when it implies none. `extrude_edges` takes no distance, unlike `extrude_faces`: a closed rim's owning faces point radially outward all the way round, so their mean normal is zero and an `offset` would silently do nothing — and a parameter that silently does nothing is worse than no parameter. **Neither op guesses at winding.** Each new quad traverses its shared edge opposite to the face already on it, which is what "consistently oriented" means, and for a bridge that is true on *both* sides at once because each loop is ordered by the direction its own faces traverse it. The only thing bridge measures is which rotation of a closed loop pairs with the other, because a ring carries no starting vertex — and getting that wrong raises nothing, it just puts a visible twist in the strip.

**A built asset is an ordinary asset: `source.glb` is authored, `model.glb` derives from it.** `service.jobs.import_mesh` mints a `done` model row from GLB bytes exactly as `import_reference` mints a reference row from painted pixels — no worker run, because the artifact already exists — and the payoff is that rigging, posing, sprite sheets, the triangle retarget and every mesh export are pure functions of `model.glb` and need to learn nothing about Clay. The `source.glb`/`model.glb` split is the existing invariant rather than a new one, and it is what keeps `optimize_job`'s retarget working on something a user modelled. Grounding applies (a failure is logged and swallowed, as everywhere else that runs on a GLB already on disk); `validation.check_glb` refuses non-GLB bytes and a GLB with no primitive at the door, before a job directory exists; and `params["built"]` is an *input*, so it stays out of `DERIVED_PARAMS` and is what `rerun_job` reads to refuse a reroll or a remesh **above** the `input.png` check — below it, a built asset was refused with the reference message and sent the user to hand-edit an image that never existed. `assets/<job_id>/build.wblk` follows the `paint.ora` precedent — the filename keeps its pre-rename spelling for the same reason, a compatibility contract with every asset directory already on disk (absent from `MEDIA`/`LISTED`, never served) but deliberately has **no** staleness rule: nothing rewrites a built asset's source behind it, and a later retarget makes `model.glb` a derivative of the document rather than making the document wrong.

**A painted reference is a job row with no worker run.** `jobs.import_reference` mints a `done` reference from pixels the user drew -- `JobStore.create` takes an explicit status for exactly this, in one statement, because a create-then-claim pair leaves a window in which the worker's poll picks the job up and tries to run it. `assets/<job_id>/paint.ora` is the layered source behind a hand-edited reference (the filename keeps its pre-rename spelling, a compatibility contract with every asset directory already on disk), following the `input.orig.png` precedent: deliberately absent from `MEDIA`/`LISTED`, never served, and treated as **stale when it is older than `input.png`** -- a revert or a regenerate rewrites the reference without touching the layers, and resurrecting them would show an edit of an image that is gone. The flat half still goes through the untouched `files.save_edited_image`, so the original backup, `hand_edited`, the reference re-measure and the staged replace are all unchanged. That staleness rule decides the **write order**, and it is the opposite of what it looks like: `inker_mode._save_linked` writes `input.png` *first* and `paint.ora` second, because writing the layers first would leave the reference newer than them the moment the save completed — every save marking its own layers stale, and the next open silently flattening a layered document to one layer. Crashing between the two then leaves the layers older than the reference, which is exactly the verdict a half-finished save deserves.

**One GL context, and imgui draws through moderngl.** `studio/imgui_backend.py` reimplements imgui's OpenGL3 backend on moderngl rather than using imgui-bundle's own, which draws through PyOpenGL: moderngl caches GL state, so raw `glBindTexture`/`glUseProgram` calls behind its back leave the viewport rendering with whatever the panels last bound. The same bridge is why `widgets.texture_ref` *registers* a texture as well as wrapping it — an id the renderer does not know maps to no moderngl object, and every image in the UI comes out as the font atlas. Registration has a matching half: a texture must be `forget_texture`d before it is released, or the backend keeps a dead object under a GL name the driver will reuse. `ThumbnailCache` also defers the release itself by one frame and never evicts an entry handed out during the current frame — a card asks for its texture while the UI is built and the pixels are not read until the backend draws, so freeing inside that window frees something the draw list still points at.

**A merged font's base wins every collision, and a rendered frame is the only thing that can see it.** `fonts.load` builds each face as Inter with `lucide.ttf` merged in, and imgui resolves a codepoint against a merged font's sources **in order**: the base font wins and a merged source only fills gaps. Inter ships 745 Private-Use-Area cmap entries — stylistic-set alternates like `divide.squared`, `question.squared`, `less.circled` — and Lucide 0.525.0 assigns its icons across U+E038–U+E682, so the two overlapped on 478 codepoints and **41 of the 83 constants in `icons.py` drew an Inter glyph instead of an icon**: Settings a division sign, Clay's ruler a question mark, Quit a digit six, and Save, Search, Plus, Undo, Redo, Play, Check, Pencil, Eraser, Brush and Palette all punctuation. It shipped because nothing below a rendered frame can see it — the GL smoke suite runs on imgui's default atlas where every icon is a missing-glyph *box* by design, and its own docstring says it asserts nothing about what anything looks like. The fix is at the font (`scripts/strip_font_pua.py`, idempotent, re-run after any font bump) rather than at the loader, because imgui 1.92's Python binding exposes no glyph exclusion on `ImFontConfig` and the two alternatives are worse: making lucide the base source would take the line metrics from a font with ascent 1000 / descent 0, and remapping lucide's codepoints would break the one rule `icons.py` states — that its numbers come from a named release's `info.json` and are never guessed. `tests/test_fonts.py` asserts the wider invariant (no PUA in any Inter face at all, not merely none that collides today) because the icon set grows and a future collision would be attributed to the new icon rather than to the font.

**`scripts/screenshot_modes.py` is what "somebody looked at it" means here.** It drives the **real** `App` — `setup_window`/`setup_runtime`/`setup_context` and `App.frame` — and reads frames back off the default framebuffer, one PNG per mode per palette, so the dispatch exercised is `_build_ui`'s own and the fonts are the loaded atlas. Reimplementing the mode dispatch in a harness would be a second dispatch, which is the thing `modes.py` is data rather than a callback table to avoid. `--seed` opens an Inker canvas and a Clay model through the same entry points the buttons call, because both modes' empty state is exactly the frame that shows none of their controls. It found four defects in one pass, and three of them share a cause worth stating on its own: **the smoke suite runs at UI scale 1.0 and nothing else does.** `theme.apply` sets `item_spacing` through `sp()`, so a grid that subtracted a literal `8` for its gaps was right at 1.0 and short by 4.8 px per gap at 1.5 — the Inker toolbox lost its fifth column and Clay its fourth button, on the only scale anybody runs. `widgets.grid_width` asks the style instead; `widgets.labeled_slider_int`/`_float` are `labeled_combo`'s rule applied to the control that was missing it (imgui draws a slider's label *outside* the widget, so nine full-width sliders had no visible name at all); and `widgets.card` takes `no_scrollbar`, since a scrollbar in a fixed-size tile is a symptom that worsens itself by taking its width out of the content region.

**Startup is three phases, and `run` drives them itself so a splash can cover the slow one.** `setup_window` (DPI, pygame, GL attributes, moderngl, fonts, theme) is fast and must come first; `setup_runtime` is the slow half — doctor, the worker, and the out-of-process bpy probe — and runs on a plain worker thread while `studio/splash.py` pumps frames; `setup_context` builds `AppState` and `Ctx` back **on the frame thread**, because it makes textures and textures need GL. The splash holds for `max(3 s, load time)`, and a quit during it *waits the load out* rather than abandoning a half-started runtime with a `python.exe` stranded mid-`import bpy`. `in_setup` stays true across all three, so the log still tells "never appeared" apart from "vanished after twenty minutes" — a failure to build the Ctx is a startup failure even though the window is already up. **There is deliberately no `setup()` composing the three.** It existed briefly with no caller, while two tests stubbed `app.setup` to isolate `run`; once `run` stopped calling it those stubs became silent no-ops, `run` reached the real `setup_window`, initialised pygame for real, and the live display it left behind broke every GL test that ran after it — 74 errors, none in the code that changed, and green in isolation. A convenience method with no caller is not free.

**Rendering parity is against three r170's stock pipeline, not against an idea of PBR.** The browser build never wrote a custom shader, so `viewer/programs.py` reimplements what three does: the Stephen Hill ACES fit *with* its `/0.6` pre-scale (dropping it is the classic "everything is dark" bug), the exact piecewise sRGB OETF, and the Lazarov/Karis `DFGApprox` polynomial three itself uses. The viewport background is deliberately **not** tone-mapped -- three sets the clear colour straight back to sRGB, so it is the literal hex. `viewer/env.py`'s gradient probe exists for one reason: ambient from *below*, without which a quarter of every mesh renders darker than the background and reads as holes.

**A verdict is a row keyed by job id, and it carries a copy of the settings it judged.** `service/verdicts.py` records a judgement against any finished job — a sweep unit in Review, or an ordinary asset in the 3D inspector, feeding one pool. The `vector` column is denormalized *on purpose*: `prune_jobs` deletes job rows and their directories, and the learning corpus has to outlive the assets it was learned from. So is the sweep context (`sweep_id`/`sweep_unit`/`seed`/`prompt_hash`, migration 5): matched-pair comparisons must survive `delete_sweep` taking the job rows, and rows recorded before the columns existed simply never pair. Verdicts are append-only and latest-wins per `(job_id, source)` by max id (an AUTOINCREMENT rowid, not `created_at`, which ties at the rate a reviewer presses a key); `source` stays a free string so a future `ai:<model>` judge sits beside a human rather than overwriting them. **A mesh verdict is a grade, not a bit, and `verdict` survives as a derived column with exactly one writer.** Migration 10 adds `verdicts.grade` — an integer −5..+5, model stage only — because the binary corpus failed at its own purpose: 3 accepts against 81 rejects on 2026-08-07, in which a solid slab, a smeared texture and a mesh a modeller would fix in five minutes are the same row, and a bit can say a mesh failed but never how close it came. The `verdict` TEXT column is *not* dropped: `vectors.verdict_for_grade` derives it at record time, which is what leaves prune retention, the judge's label reads, the `latest_verdicts`/`unverdicted_models` SQL and every findings-v3 reader unchanged — and one writer is what stops that from being the two-spellings hazard, which is also why `record_verdict` **refuses** a caller-supplied `verdict` on the mesh stage rather than checking it. Existing rows are backfilled ±3 and the cut is `grade >= 3`, and those are one decision with two names (`BINARY_GRADES["accept"] == USABLE_GRADE`, asserted rather than commented): a cut above +3 would silently demote every row the migration just wrote, one below it would claim a grade nobody recorded was already usable, and ±3 is the mildest grade preserving what a binary reviewer actually asserted — leaving ±4/±5 for judgements they had no key to make. `docs/measurements/2026-08-09-grade-scale.md` is where every one of those numbers is argued, per the rule that a constant the stored corpus is keyed on gets its document first. **Tags replace reasons and are legal at every grade**: the five bad spellings are the old `REASONS` tuple frozen (the corpus carries those exact strings in the same `reasons` column and there is no alias table, so a rename would split the evidence rather than migrate it), five good ones join them, and the two vocabularies are **disjoint strings** — which is the whole licence for one storage namespace, since polarity is then recoverable from the tag itself and the findings writer splits by membership, keeping `bench/findings.py` pure-stdlib. Five per polarity is load-bearing rather than tidy: it is what makes Ctrl+1-5 and Shift+1-5 map positionally with no second table naming which digit is which. **Image-stage labels stay binary and their `grade` stays NULL permanently** — they feed binary logistic probes, so a grade would be thresholded straight back to a bit, and the two-key loop is what makes a hundred-image pass viable at all; `record_verdict` refuses a grade there and a verdict on the mesh side, so each stage takes exactly its own argument. `service/findings.py` aggregates them into the same `bench_dir/findings.json` the generate panes already read through `bench.findings.load`. **The marginals are confounded, and it is deliberate:** a verdict credits *every* `param: value` in its vector — the price of letting daily use feed the hints at all. The unconfounded answers live elsewhere in the document: `vectors` ranks whole configurations **by Wilson lower bound of the usable rate** (`wilson_low`, z=1.96 — a raw-rate sort let a lucky 5/5 outrank a 19/20; the raw rate is still displayed beside the floor), with `mean_grade` as the **first tie-break and deliberately not the primary key**: a mean−SE bound degenerates at n=1 (sd is zero, so the bound is the mean), which re-creates the lucky-5/5 pathology in a new coordinate system, and over the freshly backfilled corpus every grade is ±3 so the mean is an affine function of the usable rate anyway. A bucket with no grades sorts last among its ties rather than as 0.0 — `Filters.order`'s unanswerable rule, and here it matters twice over because 0 is a real grade meaning "no opinion either way" and so cannot also stand for "nobody has said", and `comparisons` holds matched pairs recovered from sweep structure — two rows pair iff same `(sweep_id, source)`, same `seed`, vectors differing in exactly **one** key (absence is a side, rendered `"unset"`; never parsed from a `sweep_unit` label). `VECTOR_PARAMS` is an allowlist rather than "params minus DERIVED_PARAMS", so adding a derived value to queue.py can never silently widen what a verdict is filed against; floats are rounded to 6dp because an imgui float32 slider hands back `0.6000000238418579`. **It lives in `warlock/vectors.py`, not `service/`** (re-exported by `service.findings`), because queue.py may not import `service` and the worker needs the same vocabulary for observations — a rule that since 2026-08-11 covers the `_q_*.py` siblings holding the rest of `Worker`'s methods as well, and is pinned rather than stated by `tests/test_queue.py::test_the_worker_never_imports_service_studio_or_imgui`, which AST-walks `queue.py` and every `_q_*.py` including function-body imports — and the grade scale and tag vocabulary live there for a *second*, unrelated reason that lands in the same place: `service/verdicts.py` imports `service/findings.py` at module top, so a constant both need cannot live in the importer. `findings.json` is at version 4 and strictly additive — every v3 key keeps its value and its meaning, because `accepts` is now counted off the derived cut and computed identically, so a v3 reader is correct on a v4 file and `bench.findings` renders the v3 strings character for character on a file that carries no grades. A comparison's win is the **higher grade** (over the backfill that is exactly the old accept-beats-reject predicate, and on graded rows it says strictly more: a +4 beating a +1 was filed as a tie), with `_grade_of` falling back to the same `BINARY_GRADES` table the migration used so a pre-migration row is the same evidence as a migrated one.

**An observation is the verdict table's pattern applied to machine measurement, and nothing deletes one.** `queue._observe_finished` appends one `observations` row per model-stage job that reached a terminal status — config vector, sweep context, and `vectors.observation_metrics` (worst/mean hole fraction from `mesh_audit`, watertight/triangles/ready from `mesh_report`; a malformed piece costs its own key, never a raise) — via `Worker._record_observation`, which logs-and-swallows like `_audit_mesh` because a diagnostic must never fail a job whose mesh is on disk. That is what lets evidence accumulate on every *generation* rather than every review: findings marginals carry a `metrics` sub-object (same confounded semantics), a bucket can exist with zero verdicts, the panes hint `"holes 3% · watertight 71% (21 meshes)"` below the verdict threshold, and comparison entries carry paired metric deltas the moment a sweep finishes. `import_mesh` and the retarget re-audit deliberately write no observation — the corpus is about what generation settings produce.

**Terminal status, not `done`, and the composition gate is why.** `_process` calls `_record_observation` for `error` as well, because a job refused at `reference.prepare` *is* a measurement of the settings that drew the reference — the 17 refusals of the 2026-08-07 rogue sweep wrote nothing at all, so a reader saw each checkpoint's accept rate among the references that survived, which flatters exactly the checkpoints that fail most often. A **cancel** still writes nothing: that is the user changing their mind, and it is the one status that discards the artifacts a row would describe. The metrics decide, not the status — `observation_metrics` returns `{}` for a job with nothing measured, and that is still what keeps an empty row out. The refusal keys are `refused` plus one `refused_<code>` per `reference.REFUSAL_CODES` (`empty`/`occupancy`/`edge`/`multi_object`, index-aligned with `Report.reasons` because a rule that grows a sentence and no code makes a refused job look like a passing one), and **a job that passed the gate records `refused: 0.0`** — the mean is only a *rate* if the passers are in the denominator, and over refusals alone it is 1.0 by construction. `service.findings._metric_summary` averages every `refused*` key it finds into `<key>_rate`; the hint tier renders it first and says **references**, never meshes, because a refused job never reached one.

**Findings are also scoped per subject, and the label is half the feature.** `findings.json` v3 carries a `prompts` section — the same marginals again, one set per `prompt_hash`, built by the same `_marginals` the global ones are so a scoped number means exactly what a pooled one means over a narrower set. Confounding across *settings* is the accepted price of letting daily use feed the hints; confounding across *subjects* is not the same bargain, and it was demonstrated rather than predicted (the regenerated file reported `bg_removal: auto` at n=84 when only 80 were rogue-sweep units, the other four old wood-prompt rejects). `bench.findings.hint(..., prompt_hash=...)` prefers the subject's own evidence, falls back to the pooled corpus rather than to silence, and appends `· this subject` / `· all subjects` either way — an unlabelled fallback is the silent mixing the scoping exists to stop. Passing nothing keeps the old behaviour to the character, label included: a caller that does not know its subject makes no claim about one. A row with `prompt_hash == ""` (an upload, a painted reference) joins no scope at all, or every unrelated one of them pools into a single subject that does not exist. Scoped buckets keep only the four fields `hint` reads, because there is one per distinct prompt.

**But an appended row is not a finding until something recomputes the file, and the worker cannot ask.** `service.findings.refresh` is a task, and queue.py runs on the asyncio thread knowing nothing about tasks or panes — so the *only* place a finished generation is noticed is `main.App._refresh`'s `announce` callback, which mirrors `_observe_finished`'s own condition and marks `AppState.findings_dirty`. A **flag pumped every frame** (`review_mode.refresh_findings` / `pump_findings`), never a direct submit: `TaskRunner.submit` refuses a key already in flight and nothing re-arms it, so a burst of verdicts recomputed over the set as it stood at the first press, and the request following the *last unit of a sweep* — with nothing after it to pick anything up — was dropped for good. The flag is cleared only when the submit is accepted. Both verdict paths go through the same request rather than keeping two spellings of Review's key, and the end-to-end property (`findings.json` carries an observation with **no verdict filed**) is pinned in `tests/test_findings_service.py`, not just the aggregation — testing `aggregate` alone is exactly how a recompute nothing triggered survived review.

**A verdict now says which question it answers, and the third value is the whole reason the column exists.** Migration 7 adds `verdicts.stage` — `model` | `reference` | `blank`, defaulting to `model`, which is what every row written before it is about. Migration 10 gave that column a second job: it is what decides which argument `record_verdict` takes, since **the mesh stage is graded and the image labels stay binary with `grade` NULL**. The instinct is a two-value column mirroring `jobs.stage` and recovering the intent by joining back to the job, and it breaks for the reason `verdicts.vector` is denormalized at all: `prune_jobs` deletes job rows, so a label whose meaning depends on one is uninterpretable exactly when it matters. Two of the values are *intents over the same artifact*, because in 2D mode the image is the deliverable — a dramatic plate with pillars and a cast shadow is a better **asset** and a worse **blank**, and those are opposed objectives rather than one refined. So a reference image carries two independent labels, which is also why intent may not live in `source`: `latest_verdicts` keys on `(job_id, source, stage)` now, and without stage in that grouping one answer would silently supersede the other. Three consequences. `db.unlabelled_references` is a genuinely different query from `unverdicted_models` and cannot be it with a parameter — that one filters `status = 'done' AND sweep_id IS NULL`, excluding the two things a labelling pass most needs (an errored job, i.e. a reference *refused at the composition gate*, which is the most informative negative available; and sweep units, which are the entire corpus) — and it derives the population it lists from the label stage through `LABEL_POPULATION`, because the product question is about a reference-stage job's image and the blank question about a model-stage job's. `record_verdict`'s `status == 'done'` rule is about **the artifact a verdict judges**, not the status word, so an image label needs the *image* (a refusal has one; the gate runs after the picture is drawn) while the mesh side is untouched — an accept filed against a mesh that never existed poisons the corpus permanently. And `findings.aggregate` filters to `stage == 'model'` **at the top**, which is more than §7 asked for and deliberately: `_marginals` alone leaves `vectors` advertising an image label as a ranked mesh configuration, and `_comparisons` pairing a blank label against a mesh verdict *on the same unit* as a matched pair.

**The judge is a linear probe and it is advisory, which is the only claim it may make.** `judge.py` is pure in the `vram.py`/`memlog.py` sense — stdlib plus numpy plus `bench.metrics` for the embedding (one DINOv2 loader in the repo, with its `local_files_only=True` and its per-device cache, rather than a second answer to "which weights"), nothing from `service`/`queue`/`studio`, and `None` rather than an exception for every way of having nothing to say: no weights, no probe, an unreadable PNG, a width mismatch after a model swap. **`score` returns a probability and there is no threshold anywhere in the module**, because a threshold is a constant the stored corpus is keyed on and owes a `docs/measurements/` document first. Four rules around it are load-bearing. **The probe is trained on pixels, never on the audit scalars** — AUC(`hole_worst` → reject) is 0.115 on the existing corpus, not weakly informative but *backwards*, because a slab has no holes and `meshaudit` scores the dominant failure mode as perfect; a probe fitted to those numbers would need a sign flip to beat a coin and would then be fitting the slab artefact, and the same inversion disqualifies `hole_worst` as a sanity check *on* a probe. **Labels must be human**: the gate's own refusals are tempting free labels and are the rule's own output, so a probe fitted to them reproduces `reference.py` including its blind spots — and `baseline s23` passed those rules and is still a poor blank, which is the case a learned judge exists to catch. **`fit` returns `None` rather than a probe below `MIN_PER_CLASS` of each class**, because the corpus as it stands is 3 accepts against 81 rejects and a probe fitted to that learns "reject" and scores 96% doing it, which is worse than no probe because it is believed. And **`judge.STAGES` is spelled exactly as `verdicts.STAGES` is** (`model`, not `mesh`), pinned by a test rather than by a comment: a translation table between two names for one thing is how the two drift, and the drift would show up as a probe trained on the wrong population. The mesh probe is declared and unbuilt — `TODO.md` §8 is blocked on a corpus with positives in it, and its pooling over eight views is a decision to make with data.

**Labelling is a second loop in Review, and the flag is the same flag.** `review_mode.LabelPass` owns the keyboard whenever it is open (`_label_key`, checked before every verdict binding, so a keypress about a picture can never be filed as a verdict about a mesh), offers two keys and no second step — grades and tags are mesh-stage concepts, and eleven values plus ten tags is far more than a two-second-per-image pass can carry — and keeps an answered row **in place** rather than removing it, since a shrinking grid renumbers itself under the cursor mid-pass. Three of its rules are lessons from elsewhere applied verbatim. Thumbnails upload **one per frame** (`next_thumbnail`), which is `viewer/sheet.StripRender`'s rule at a hundred cells rather than sixteen, and an un-uploaded cell draws a same-size placeholder so the grid never reflows under a click. Retraining is a **flag pumped every frame** (`AppState.judge_dirty` / `pump_judge`), never a direct submit, for exactly the reason `findings_dirty` is one — and it carries the *stage* rather than a bool, since a pass is about one question. And `judge.status` is read **once per listing task and then kept current by arithmetic**, because it is a whole-table scan plus a stat and the panel draws every frame. `by_score` **sorts and never filters**: a judge that hid what it disliked would make its own mistakes invisible, which is the filter bubble, and unscored rows sort last rather than as 0.0 because "no opinion" is not "bad".

**Blinding a review hides the order, not just the label.** `ReviewState.blind` renames every unit to an id prefix *and* presents them in `blind_order` — sorted by a SHA-1 digest of the job id, so the presentation is independent of enqueue order and identical in every process (`hash()` is salted per run, which would re-present the same units under different names tomorrow). Hiding the label alone blinds nothing: `sweeps.expand` enqueues the baseline first and then one unit per axis value, so in a two-arm sweep position names the arm. It is a *session* flag and is not persisted, like everything else in `ReviewState`, because a review resumed blinded without saying so is worse than one that starts unblinded; and `label(state, unit)` takes the state rather than a keyword flag so a call site that forgot it is a TypeError on the first frame rather than an unblinded label inside a blind review.

**A gltfpack tier is qualified by data, and the harness may not consume its own corpus.** `tiercheck.py` is pure (stdlib plus `glbio`) and reads the **JSON chunk** of both GLBs rather than going through trimesh, which merges a scene into one mesh with one material and so destroys the exact property under test — whether a multi-material mesh still assigns each primitive its own material after a simplify pass. Every rule is "not worse than the source", never "identical to an ideal", since a rock with one untextured material is a legitimate input; the accepted cost is that a qualification could pass by preserving nothing, so a source that was already missing something says so in `notes` beside the verdict. It also fails an output that **requires an extension the source did not** — the one loss no UV or texture count would catch, because the viewer's loader refuses a file needing `KHR_mesh_quantization` and `-noq` exists to stop gltfpack writing it. `scripts/qualify_tiers.py` drives `optimize.run` (the same binary and flags a job uses, injected so the table's own behaviour is testable without gltfpack) and writes **only** under its output directory: `service.jobs.optimize_job` rewrites `model.glb` in place and deletes the derived artifacts describing the old mesh, so driving *it* would consume the accepted meshes the qualification needs — and a harness that destroys its inputs can be run once. Its corpus defaults to the meshes a human accepted and it refuses to run when there are none, because whether a tier *preserves* something cannot be judged on output that is already broken.

Every mean carries `counts[metric]`, its *own* sample size: `n` is the bucket's, and a `meshreport` that failed or came back `invalid` leaves an observation with holes and no watertight flag, so one reading in twenty-one was being advertised as twenty-one. The reader thresholds and labels per measurement, and says **meshes** rather than runs — a model-stage observation credits the whole 2D taxonomy its job was promoted with, so these lines appear under prompt controls where "21 runs" would read as a claim about the picture. UI strings for all of this stay inside imgui's default Basic-Latin+Latin-1 atlas range: `·` (U+00B7) is safe, a real `≥` or `Δ` renders as the missing-glyph box, hence `"(41%+)"` and `"worst-hole"`.

**A derivation is not a save.** `app_ctx.save_key` / `derive_key` are two namespaces because `main._on_task_done` toasts `"Saved to <result>"` for every finished `save:` key — and `derive.get_file` returns the path *inside* the job directory and is never `None`, so the pixel preview submitted under the save key told the user a file had been saved somewhere they never chose. `Ctx.artifact_busy` checks both, which is what keeps a preview and an export of one artifact from ever describing different files.

**A sweep is a family of settings vectors on the live queue, and it goes through the front door.** `service/sweeps.py` expands a `SweepPlan` into `UnitPlan`s (the OFAT fan-out is the convenient builder; hand-picked `vectors` are equally expressible) and submits each through `service.jobs.create_job` and nothing else — same validation, same VRAM admission, same directory-before-row ordering. Membership is two *columns* (`sweep_id`, `sweep_unit`), not params keys: the list filters on them, and because `rerun_job`/`promote_to_model` copy params only, membership can never leak onto a reroll — which sidesteps `DERIVED_PARAMS` instead of bending it. Admission is **all-or-nothing**: every unit is validated before a single row is written, and one bad unit refuses the whole sweep naming itself. Units are ordered into server-config groups (base config first) to minimise trellis restarts, and that ordering is best-effort only — correctness lives in `Worker._generate`, which calls `trellis.ensure_config` with fully *resolved* values on every model-stage job, so an ordinary job after a sweep unit restores the config itself and no bookkeeping can go stale. `ensure_config` adds no spawn site: it writes the fields `_argv` reads and stops a running server whose config differs, letting the existing lazy `ensure_started` do the restart. `Filters.matches` hides sweep units from the library, because one launched sweep otherwise buries a workshop.

**Mesh candidates are columns, and "Keep" dissolves the group rather than flagging a winner.** Migration 6 adds `candidate_group`/`candidate_index` to `jobs` for exactly the reason migration 4 added `sweep_id`/`sweep_unit`: the library filters on it, params is a JSON string sqlite cannot index into, and — the half that matters — `rerun_job`/`promote_to_model` copy *params* and nothing else, so membership can never leak onto a reroll, which sidesteps `DERIVED_PARAMS` instead of bending it. `service.jobs.promote_candidates` is the entry point (the generic `count > 1 requires output=reference` refusal in `create_job` stands unchanged; candidates are the deliberate exception and are reachable only here), and every candidate is an ordinary mesh job through `promote_to_model` — same validation, same per-job VRAM admission, same directory-before-row ordering. **Candidate 0 keeps the requested `mesh_seed`, the rest draw fresh ones**, the idiom `create_job` already applies to reference candidates. Admission is all-or-nothing like a sweep's, and it needs *no* validation pass of its own: every candidate is the same job but for a pre-checked seed and `promote_to_model` refuses before it writes anything, so a refusal can only land on candidate 0 with nothing yet written — duplicating the check list here is the drift `sweeps._check_unit` has to work to avoid. `candidate_group` is NULL for an ordinary job *and* for a decided one, so `Filters.matches` asks one question and `keep_candidate` clears the column for the **whole group** in one statement: a winner flag would leave the losers hidden with nothing to reach them by, since the picker (`studio/candidates.py`, pure; `panes/candidates_panel.py` draws it, above the inspector's header so it survives an empty selection) derives itself from the rows rather than from remembered state precisely so a restart cannot strand a group. `candidate_index` survives the dissolve and is read by nothing, the forensic half `sweep_unit` is. Keeping never deletes: the losers are *named* and offered to `library.delete_asset` behind the ordinary confirm, and picking a candidate only calls `state.select` — `_sync_viewer` owns the pose guard, `viewer.pending` and the off-thread parse, and a shortcut into `load_model` from the picker would reproduce two of those three and get the last one wrong.

**A sprite draft is write-once, and the sidecar is what says it exists.** A `sprite_synthesis` job invents a sheet from one 2D reference: two candidate 1024px atlases from two seeds, sliced on a *fixed* grid (`pipelines/spritesynth.GEOMETRY` — turnaround 2x2 at 512, walk 4x4 at 256), matted, put on a shared baseline, reduced in one NEAREST pass and quantized to one palette across the whole atlas. Four rules hold it together and each is the same shape as a rule already here. **Nothing is published until both candidates are assembled**, and then in one order — both PNGs, then `<id>.json` last, exactly as `_sheet`/`_pixel_sheet` publish — so `rigging.list_sprite_drafts` treats the sidecar as the completion marker and a cancelled run leaves nothing at all. **A draft is never rewritten in place**: every generate run mints a fresh `draft_id` at the door and the only mutation is delete, which is precisely what makes `sprite_panel.draft_records` sound behind a *directory* mtime stamp — the racily-clean hazard `panes/stamps.py` documents can cost that listing a draft for 50 ms and can never make a cached record wrong. **The grid is never re-detected from pixels**: adoption slices on the sidecar's own `cells` rectangles, so a mis-registered generation is an editable document rather than an unopenable one. And **a warning is never a refusal** — `structural_warnings` reports `empty` / `clipped` / `occupancy` / `unmatted` as machine codes beside sentences (the `reference.REFUSAL_CODES` split, for its reason), because the deliverable is a *pair* the user compares and discarding one leaves them judging a draft against nothing. The pose guide is fed to the canny ControlNet **directly and is not run through `cv2.Canny`** — it is already white line art on black, and detecting edges on it returns the outline of every stroke, i.e. two lines where the guide means one. The heavy matting model runs **once, on the source**, never per cell: it is ~11.5 s an image, and the "plain background" clause in the prompt is what earns the cheap per-cell corner fill instead.

**The cell order is held twice and a test is its only owner.** `pipelines/spritesynth` decides where a cell sits in a generated atlas; `studio/inker/animation.DirectionalLayout` decides what timeline frame *i* means once that atlas is opened. They cannot share code — the inker package imports nothing outward (`tests/inker/test_sheetout.py` pins the exact set) and `pipelines` modules run inside worker and Blender processes where `studio` is not importable — so `DIRECTION_ORDER`, `DIRECTION_YAWS` and the per-kind grid exist twice, and `tests/test_sprite_geometry_agreement.py` is the **single place** the copies are checked against each other. If it fails, a draft generated with the back view bottom-right opens in Inker as frame 2, silently, until somebody plays the animation.

**A layout is additive metadata about a grid whose pixels are already correct.** `Animation.layout` is construction-time state like `Document.matte`: no V1 op edits it, and a whole-canvas snapshot restores by mutating the existing `Animation` in place, so it survives undo with no snapshot change. It rides `animation.json` as a top-level `"layout": {"kind": ...}` written **only when set** — the version stays 1 and a layout-less document's member is byte-identical, the same additive rule `tags[].direction` set — and it is read in its **own guard** outside the block that rebuilds the timeline, so a malformed or unknown layout degrades to `None` and never falls the file back to a flat read. On the way out, `sheetout.plan_frames(..., layout=)` replaces the wrap with the sheet's own fixed grid and **refuses a frame count that no longer fills it**, naming both numbers: padding would emit an atlas with a hole where "back, frame 3" belongs, which is the one outcome a game does not notice until it plays the animation. `inker_mode.export_sheet` raises that refusal on the frame thread before the file dialog, with the engine's `ValueError` as the backstop. `snapshot` returns a 4-tuple and `compose` takes the layout **positionally**, so `compose(*snapshot(doc))` still holds — a keyword-only fourth element would have made that spelling drop the grid in silence.

**A new job kind is four edits, not one.** `sprite_synthesis` is the current example and the checklist is: a branch in `Worker._generate` *and* one in `_discard_artifacts` (which must name only this job's own files — the source directory holds every earlier draft, each from a different and successful job); a branch in `vram.estimate`, because an unlisted kind falls through to `return 0.0` and the admission gate becomes a no-op that refuses nothing; and a phase table in `progress._PHASES_BY_KIND`, because `ProgressBus.update` falls back to `(0.0, 1.0)` for an unknown phase and would drag the bar back to zero. The last one is why `_sprite_synthesis` maps `on_step` into its own per-candidate phase rather than reusing `Worker._t2i_state`: that helper emits `t2i_load`/`t2i_sample`, which `PHASES_SPRITE` does not carry.

**The GLB loader is hand-rolled on purpose.** trimesh discards a scene root's transform -- which is exactly where `normalize_glb` puts the grounding transform -- and has no notion of a skin. `viewer/gltf.py` keeps the node graph live after loading, because posing is setting a joint node's local rotation and recomputing world matrices. Being hand-rolled means the spec's edges are this file's problem, and three of them are load-bearing. A file whose `extensionsRequired` names anything outside `SUPPORTED_EXTENSIONS` is **refused**, because `KHR_mesh_quantization` — which the vendored gltfpack writes with `-c` — decodes as silently wrong geometry otherwise. An accessor's `normalized` flag is honoured (`Reader.decoded`), or a `ushort` UV reads back as 65535. And a texture that cannot be *decoded* is skipped exactly as one that cannot be *found* is: the stated policy is that an image is a cosmetic loss, and raising turned one corrupt map into "this file will not open" for an intact mesh. On the draw side, a zero-scaled node's normal matrix falls back to the identity rather than raising `LinAlgError` out of the frame.

## Stack

- Python 3.12+, uv-managed (`uv sync --extra studio` — dev tooling is a default dependency group, not an extra; `uv run pytest`, `uv run ruff check .`). No web framework: `httpx` remains only because `trellis-server.exe` speaks HTTP on a local port.
- Optional native kernels: `pwsh native\build.ps1` → `vendor/warlockc/warlockc.dll` (MSVC, clang or zig; the script picks). Not needed to run anything — see the native-kernel invariant above.
- `trellis-server.exe` is a vendored compiled binary (`vendor/`), not a Python package — confirm behavior against its actual CLI help / exposed routes, not against the upstream TRELLIS project's docs
- **An image model is a registry spec, not a directory.** `models.py` owns `BASE_MODELS` / `STYLE_LORAS`: a `BaseModel` carries its dir name *and* the settings it must run at (size, steps, guidance, variant, scheduler, always-on step-distillation LoRA), because those are properties of the checkpoint — a 4-step distilled model run at 25 steps with CFG produces mush, and Hyper-SD silently degrades without trailing timestep spacing. Add a model there, never by hardcoding constants in `pipelines/text2image.py`. `guidance.py` validates and stores the selection but deliberately keeps model keys and LoRA trigger words out of `_PROMPT_FIELDS` — triggers are prepended next to `PROMPT_TEMPLATE` instead. **`family` and `residency` are declared, never sniffed.** `family` (`sdxl` | `flux2klein`) decides which encode/sample path runs — `_sample_sdxl` chunk-encodes through two CLIPs and passes pooled embeddings, `_sample_flux2` passes one 512-token string and no pooled anything — and it is stated rather than derived so a future checkpoint cannot become "SDXL-shaped" because it happened to ship a `unet/`. Everything SDXL-specific is refused on another family rather than degraded, at the door and again at the pipe: conditioning (`_conditioned`) and seamless tiles (`tile_bases()`, `create_job`) — a tile is the sharpest case, because circular padding is a `Conv2d` property and a DiT has none, so patching only the VAE would yield an image that looks seamless in a thumbnail and seams in a material. `residency` picks `.to("cuda")` or `enable_model_cpu_offload()` and the two are mutually exclusive; `vram_gib` is the peak *under that residency*, which is what `vram.estimate` charges a text job (falling back to `SDXL_GIB` for a base the registry no longer carries, the tolerance `Worker._resolve_base_key` owns for all four t2i stages, and which `_retexture` gained on 2026-08-11 — it fell straight to the registry default with no config retry and said nothing). `probe` overrides doctor's `unet/`-shaped presence formula for a layout that has no unet. **A style LoRA is the one of those three that is a *pair* rather than an architecture rule**, and `StyleLora.family` is what makes it one: `models.lora_fits` is the single owner, `loras_by_base()` is what the picker lists, and `lora_bases()` keeps its name and meaning while changing its derivation — no longer "is this SDXL" but "does the registry hold an adapter fitted to this architecture". Sharing that derivation with `loras_by_base` is right precisely where `tile_bases()`' separate spelling is: tiles are a second question with a coincidentally equal answer (and the two lists now genuinely differ), whereas `lora_bases` is the same question asking whether the map's entry is non-empty. Every consumer is that one function — `guidance.normalize`'s refusal (whose `field` names `style_lora` when some adapter fits the base and `base_model` when none does, because a highlight must name the control the sentence mentions), `_load_loras`' per-adapter filter, `settings_2d.lora_options`/`clear_unusable`, `queue`'s log-and-drop — so they cannot come to disagree about a pair. **`_apply_adapters` is gated on "is there anything to disable", never on family**: the family early return it replaced was wrong for SDXL too (`turbo` has no base LoRA, so a host with no `loras/` called `disable_lora()` on a pipe with no PEFT state). And it must call **`enable_lora()` before `set_adapters()`** — `disable_lora()` sets `_disable_adapters` on every PEFT layer and `set_adapters()` writes only the scaling, so one job generated without a style silently switched every later job in the process to no style, for the life of the resident pipe. It reads as working because the trigger words are still prepended, which is exactly how it survived: the output *does* change when a style is picked, it just is not the adapter doing it (`docs/measurements/2026-08-10-pixel-art-klein.md`). A `default_weight` is a multiplier on the scale the adapter's own metadata declares, so an entry trained with `use_rslora` (α/√r = 16 rather than α/r ≈ 2) needs a default an order of magnitude smaller and it is *measured*, never taken from a model card.
- **One base model resident at a time.** The 32 GB card holds trellis (~16 GB) plus a single SDXL-class pipe (~7 GB) and not two, so `Worker._get_text2image(base_key)` unloads the previous pipe (via `asyncio.to_thread`) before building the next. Style LoRAs are the opposite: adapters on the resident pipe, switched per job with `set_adapters()` and no reload. A `residency="offload"` spec is the one that is *not* fully resident: FLUX.2 klein is ~16 GB whole, which would put coexist out of reach, so it streams one submodule at a time and peaks near its recorded 10 GiB — slower per job, but it displaces nothing.
- SDXL-Turbo (`models/sdxl-turbo`) is the default because FLUX is gated — **both `dev` and `schnell`**, and 12B params won't coexist with trellis anyway. All weights are one-time manual `hf download`s under `WARLOCK_T2I_ROOT` (default `models/`); `WARLOCK_T2I_DIR` still relocates the `turbo` entry only. See `pipelines/text2image.py`
- **A skeleton is a JSON template, not code.** `src/warlock/templates/*.json` hold normalized landmark joints in a unit bbox (Blender axes: +X the subject's left, −Y forward, +Z up; x/y span −0.5..0.5, z spans 0..1). `rigging.fit_template` scales them onto the measured mesh bbox. Add a skeleton by adding a file, never by hardcoding bones in `blender_worker.py`. Fitting is bbox-proportional and deliberately approximate — the fitted positions are recorded in `rig.json` so a later "adjust joints" pass can correct them without re-rigging.
- Rigging is the `rig` extra (`uv sync --extra rig`). bpy ships **cp313 wheels only**, so the requirement carries a `python_version` marker — without it the whole project becomes unresolvable on 3.12 rather than just losing rigging. Missing bpy is non-fatal everywhere: `doctor.blender_check` reports it and the UI hides the rig controls.
- **`src/warlock/bench/` is the package; the repo-root `bench/` is its output directory** — two different things one word away from each other, so both are written out in full below and wherever else the distinction matters (`bench/findings.json`, `bench/runs/`, `bench/calibrate/` are *outputs*). The package is the *regression* half only — the fixed suite, the recipes, the manifest, `score`/`calibrate`/`views`. The parameter-sweep half (`src/warlock/sweep.py`, `verdicts.py`, `report.py`, `src/warlock/bench/sweeps/`) is gone: it stood up its own `Runtime`, which collides with a running app. `src/warlock/bench/findings.py` stays as the pure-stdlib *reader* the panes import; `src/warlock/service/findings.py` is what writes the file into the root `bench/` directory.
- `docs/` holds four things now: this invariants reference, the manual (`docs/manual/`, which `tests/manual/test_docs.py` validates), the measurement documents under `docs/measurements/` (the two A6 and A8 produced, the audit-resolution one that justified moving `REQUEST_PATH_RESOLUTION` to 1024, the seam-threshold calibration and the re-texture bake), and the ComfyUI research note `docs/REPORT.md`. A constant the stored corpus is keyed on gets a measurement document before it changes — that is the pattern `trellis_band`, `mesh_hole_max` and `SEAM_MAX` all set. **The live roadmap, and the only one, is `docs/TODO.md`** — it is the one place outstanding work is written down. Since 2026-08-10 that file is the UX/UI review report that replaced `docs/LEFTOVERS.md` (deleted the same day; git keeps it). Every roadmap, plan and survey file that used to sit beside it — `SUGGESTIONS.md`, `CLAY.md`, `NEXT.md`, `CLAY_ELEMENTS.md`, `QA_AUDIT.md`, `CAMERA.md`, `ANALYSIS.md`, the `superpowers/plans` and `superpowers/specs` trees, and, on 2026-08-08, `TODO.md`, `NEXT_ROADMAP.md`, `docs/LIST.md` and `docs/BUILD_PLAN.md` — was executed or superseded and has been deleted; `git log --diff-filter=D` finds them if an old reference needs chasing. The rule they died under is that a plan whose boxes disagree with the tree is worse than no plan, so a finished one is deleted rather than ticked: git keeps it, and the code is the record. Two consequences of the 2026-08-08 consolidation are load-bearing, and both now point into git history. The deleted `docs/LEFTOVERS.md` **preserved the old `TODO.md`'s `§` numbering**, and eighteen source, test and script files still cite `TODO.md §2`/`§3`/`§5`/`§7`/`§8`/`§10` by number — a citation reading `TODO.md §N` means the *deleted* `docs/LEFTOVERS.md`'s §N, never a section of today's `docs/TODO.md` (which has none); chase them through `git log --diff-filter=D`, and do not mint new `§N` citations against the current file. And LEFTOVERS' closing appendix kept the handful of things a diff could not carry — the build waves' file-contention map, the three departures the judge made from its own written design, and the fact that the smoke suite runs at UI scale 1.0 and nothing else does — because deleting a plan was never meant to delete the reasoning; that appendix is likewise read out of git history now.
