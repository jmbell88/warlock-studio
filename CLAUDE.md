# CLAUDE.md

This file provides guidance to Claude Code when working in this repository. See `D:\Projects\CLAUDE.md` for how this project fits into the wider workspace.

## What this is

Local AI 3D asset generator: text or image prompt → SDXL-Turbo (reference PNG) → `trellis-server.exe` (vendored native binary, not the Python TRELLIS package) → textured GLB, in a single-process desktop app: a pygame window, one ModernGL context, imgui panels drawn through it. No HTTP, no browser.

## Hard invariants

**Three threads, and the split is the design.** The pygame frame loop reads `JobStore` directly (one connection behind an RLock, so that is safe) and must never block; the `warlock-loop` thread hosts the asyncio loop the `Worker` lives on, because `wake` is loop-affine and cancellation is a coroutine; a four-thread `TaskRunner` runs everything that blocks -- exports, Blender bakes, prune, the tokenizer. `studio/runtime.py` is the old FastAPI lifespan, port for port. Progress needs no protocol at all: the frame loop calls `worker.progress.snapshot()` directly.

**The service layer is the only business logic.** `service/` holds what `app.py`'s route bodies used to, as plain synchronous functions taking a `WarlockService` first and raising `service.errors` exceptions. The panes call it, the tests call it, and nothing else exists between the UI and the queue.

**Single sqlite3 connection, serialized by an explicit lock.** `JobStore` (`db.py`) wraps one `sqlite3` connection opened with `check_same_thread=False`, and every method that touches it takes `self._lock` (an `RLock`) first. `asyncio.to_thread` does *not* serialize anything — its default executor is a multi-worker pool, so concurrent requests genuinely land on different threads — which makes that lock the only thing keeping two `commit()`s apart. Any new method that reaches `self._conn` must take the lock too. `progress.py` is separately in-memory-only and never touches the DB from its own reader thread; keep it that way. The lock guards statements, not read-modify-write *sequences*: `params` is one JSON blob, so a caller that reads a job, edits its params and calls `set_params` performs a last-write-wins update that discards anything committed in between. Two writers on one row genuinely exist (the worker recording derived values while `POST /optimize` rewrites a budget), so a partial params write goes through `merge_params`, which reads and writes under one hold of the lock.

**Fully offline — no runtime network calls, ever.** All model weights load from local paths with `local_files_only=True`; `HF_HUB_OFFLINE=1` / `HF_HUB_DISABLE_TELEMETRY=1` are set in `src/warlock/__init__.py` and must remain the first thing the package does. Never add code that downloads at runtime — missing weights must fail with instructions for the one-time manual `hf download` (see README).

**VRAM modes (`Config.vram_exclusive`, queue.py).** Default (coexist): SDXL-Turbo (~7 GB, fully `.to("cuda")`) and `trellis-server.exe` (~16 GB) stay resident together on the 32 GB card; neither is stopped for the other, and `_maybe_evict_idle` evicts both after the idle timeout. `WARLOCK_VRAM_EXCLUSIVE=1` (read once at startup) restores the sequential handoff for a text job: `trellis.stop()` first, then load and run SDXL, then unload SDXL (`finally`) before trellis restarts. Any change to `Worker._generate` dispatch must preserve stop-before-load / unload-before-next-start **when the flag is set**, or you get an OOM that only reproduces under load, not in tests.

**`source.glb` is the reconstruction; `model.glb` is derived from it.** trellis writes `source.glb` and nothing ever overwrites it — `model.glb` is produced by optimize-then-normalize, which is why `POST /api/jobs/{id}/optimize` can retarget a triangle budget without another two-minute trellis run. The ordering is load-bearing in one direction only: gltfpack rewrites the node graph, so it must run *before* `normalize_glb` inserts the scale/translation node, and the `/optimize` route reapplies the transform for exactly that reason. `_discard_artifacts` deletes **both** files, or a cancelled job could be re-optimized back into existence. Everything else (STL, OBJ zip, FBX, `collision.glb`, `textures.zip`) is a pure function of `model.glb`, derived on first request under the per-artifact `_convert_locks` idiom, and the `/optimize` route deletes all of them because they describe the old mesh.

**Grounding is not conditional on a size.** `normalize_glb` scales (only when `size_m` was asked for), centres X/Z and puts min-Y at zero on *every* job — a pivot at the reconstruction volume's centre is a manual fixup on every Godot/Unity import regardless. Because it now runs on meshes it never used to touch, a failure is logged and swallowed rather than failing a job whose GLB is already on disk — the same rule `_audit_mesh` and the report follow. `scale_glb` survives only as a thin wrapper.

**The composed SDXL prompt is chunk-encoded, not truncated.** CLIP's text encoders cap out at 77 tokens, and with twelve optional guidance fields the composed prompt routinely exceeds that. `pipelines/prompt.chunk()` splits it into multiple <=77-token chunks on comma boundaries (never mid-phrase), each encoded separately and concatenated on the sequence axis in `pipelines/text2image._encode_long_prompt` -- the UNet's cross-attention has no sequence-length limit, only the text encoders do. A single-chunk prompt (the common case) is bit-identical to the old direct-string path. Guidance fragments in `guidance.py` stay 2-4 words each regardless: chunking removes the hard ceiling, not the soft one where a longer sequence dilutes cross-attention.

**Two different mesh measurements, deliberately not merged.** `meshaudit` answers "can you see through it" (a silhouette check, what a player notices); `meshreport` answers "will an importer accept it and will it sit on the floor" (topology, materials, budget, pivot). Only the second may use the word *watertight* — the badge used to apply that word to the first, which it never proved. Both are stored on the job and `params["mesh_audit"]` keeps its old shape so existing readers are unchanged.

**gltfpack is vendored but not yet present, and the named tiers are unqualified.** `pipelines/optimize.py`, the config field, the non-fatal doctor check and the API all exist; `vendor/gltfpack/gltfpack.exe` does not. The `raw` profile needs no binary and is the only tier the UI offers — per `docs/NEXT.md` a tier stays hidden until it has been run against a chest, a sword and a rock and shown to keep UVs, both PBR maps and material assignment. The API accepts every tier name already, so one can be exercised by direct POST before it is exposed — and `Config.mesh_profile` defaults to `raw` for the same reason: every other tier can only fail until the binary is vendored. `/optimize` refuses a job that is still `queued` or `running` with a 409, because its half of the write takes a lock the worker's `_optimize`/`_apply_scale`/`_audit_mesh` do not. Writes onto a served `model.glb` are always staged (`optimize.staged_copy`, `postprocess._staged`) — `/optimize` runs on *done* jobs, so a bare `copyfile` would let a concurrent GET read a truncated file — and the route reports (never deletes) the rig artifacts a retarget makes stale.

**Blender never runs in the app process.** `bpy` is process-global, not thread-safe, and hard-crashes (rather than raises) on some non-manifold geometry — which trellis output frequently is. So it runs out-of-process as `python -m warlock.pipelines.blender_worker`, mirroring the `trellis-server.exe` subprocess pattern. `rigging.py` is the host side and must stay importable with no bpy anywhere; `pipelines/blender_worker.py` is the only module allowed to `import bpy`, and it imports `rigging.fit_template` so host and worker can never disagree about where a joint goes. The single-sqlite-connection / single-event-loop invariant is untouched by this: `rigging.run_worker` is blocking and every caller dispatches it through `asyncio.to_thread`.

**A rig writes into the *source* job's directory, via temp names.** `rig.glb`/`rig.json` land next to the `model.glb` they were fitted to, not in the rig job's own dir — the rig belongs to the mesh. The worker never writes the served names: `rig_spec` points it at `.rig.tmp.glb`/`.rig.tmp.json` (the `.glb` suffix is load-bearing — Blender's exporter appends one to any filepath without it) and `rigging.finalize_rig` renames them into place on success, GLB first so `rig.json` — the completion gate `_attach_files` and the file route key on — never advertises a mismatched GLB. That gate alone is not enough on a *re-rig*: the old `rig.json` already satisfies it while Blender is writing, which is exactly why the temps exist. Consequences that are easy to get wrong: `Worker._discard_artifacts` must resolve `params["source_job"]` when cleaning up a cancelled rig (deleting `model.glb` there would destroy a different, successful job's mesh) and deletes **only the temps** — a cancelled re-rig must never destroy the previous successful rig's artifacts — and `queue._rig` skips `finalize_rig` when the cancel event is set, so a cancel after the solve finishes doesn't publish anyway.

**A pose is a map of glTF node-local quaternions, and that is the whole contract.** The viewer never sees a Blender bone and the worker never sees a viewer joint node; they agree because both talk about the joint node's *local* rotation. Blender composes a posed bone as `pose(b) = pose(parent) @ (rest(parent)⁻¹ @ rest(b)) @ basis(b)`, and a glTF joint's local transform is `pose(parent)⁻¹ @ pose(b)`, so `node_local == rest_node_local @ basis` exactly — `blender_worker._rest_local_rotation` is that one line, and no per-bone axis correction is involved (the Z-up→Y-up flip cancels because the exporter applies it once at the root). Two things keep the identity true and both are load-bearing: the worker imports with `bone_heuristic="BLENDER"` (the default re-aims bones at their children and silently changes `matrix_local`), and exports with `export_rest_position_armature=False` (the default writes every joint at rest and demotes the pose to an animation track). Quaternions are stored XYZW (the order `THREE.Quaternion.toArray()` used, kept because every pose on disk is in it); the worker converts to WXYZ. `studio/viewer/pose.py` imports `rigging.mirror_quaternion` rather than reimplementing it -- the browser's copy carried a comment insisting the two stay identical, which is exactly the sign convention that is wrong in a way a still image cannot show. `tests/test_rigging.py::test_a_posed_glb_carries_back_exactly_the_rotations_it_was_given` pins it by reading the exported GLB's JSON chunk directly, not through bpy.

**Poses are files, not rows.** `<job_dir>/poses/<pose_id>.json` (one per pose, so a save needs no read-modify-write and therefore no lock) with the baked `<pose_id>.glb` beside it. `rigging.pose_path` is the *only* place a caller-supplied pose id becomes a path and it raises on anything that isn't `[0-9a-f]{12}`. Overwriting a pose deletes its cached GLB — the bake depicts the old rotations. The bake itself is derived on demand in the request under the same `_convert_locks` idiom as the STL/OBJ exports, not on the job queue: it is a one-second subprocess, and putting it behind the serial GPU queue would make it wait on a trellis run.

**A sprite sheet's grid is decided on the host, never in Blender.** `pipelines/sheet.py` is pure — `plan()` works out the cells, `pack()` composites them with Pillow, `sidecar()` writes the JSON — and `blender_worker.op_sheet` only renders one square transparent PNG per cell into a scratch directory. That split is what makes the grid testable without a GPU and keeps the in-app preview, the renderer and the sidecar from disagreeing. The preview's own camera math lives in `studio/viewer/sheet.py` and has to agree with it: yaw 0 on +Z, extent `max(hypot(sx, sz), sy) * 1.12`. Three details that are easy to undo: the camera is framed **once** from the rest bbox (reframe per pose and the subject jumps between rows); the sidecar carries a **flat `cells` list** so an animated clip becomes more cells with `frame > 0` rather than a format v2; and cells arrive grouped by row so the worker re-poses once per pose, not once per frame. Column 0 is the front view — yaw 0 looks along +Y in Blender, and the templates put the subject's forward at −Y.

**Blender's glTF importer invents objects you must ignore.** It parks bone-shape widgets for an imported armature in a collection named `glTF_not_exported`. The collection is excluded from the *view layer*, so nothing renders and nothing re-exports — but the objects are still in `scene.objects`, and a unit icosphere among them trebled `_scene_bounds` and framed every rigged sheet's subject at a third of its size. Every `import_scene.gltf` in the worker is followed by `_purge_import_helpers`.

**Derived values never survive into a new job, and inputs are bounded at the door.** `app.DERIVED_PARAMS` is the single strip list for rerun/promotion — anything the worker records about a finished job's *artifacts* (`composed_prompt`, `mesh_report`, `transform`, …) must be added there when introduced, or a reroll wears a quality verdict about a mesh that doesn't exist yet. On the way in, `create_job` enforces the caps next to it (`MAX_UPLOAD_BYTES` 20 MB before decode, `MAX_IMAGE_PIXELS` 16 MP from the header before pixels decode, `MAX_PROMPT`, seeds 0..2³¹−1 via `_check_seed` on every route that takes one) and removes the job dir it pre-wrote if the DB insert fails — `input.png` is deliberately written before the row exists, so the cleanup is the other half of that ordering.

**Three panes and a mode switch; 3D mode owns no prompt controls.** The UI is settings / viewport / selected-asset inspector, with a top-level 2D/3D/Paint switch driving `state.mode` — that field is the *only* thing that decides what a pane shows. It is the two-stage pipeline that already existed made visible: 2D always submits `output=reference` and owns every field that composes the SDXL prompt; 3D starts from a finished 2D asset (`POST /api/jobs/{id}/model`, whose mesh-side Form params are all optional overrides) or an upload, and owns only mesh, rig, pose and sheet controls. A control belongs to exactly one pane — `platform` is the one field both need and it is deliberately *two* selects, the 2D pane's (a prompt fragment) and the 3D pane's (the geometry resolution), because one control cannot be owned by two panes. Anything the worker records about a finished job's artifacts still has to join `service.validation.DERIVED_PARAMS`, or an override-carrying promotion inherits a verdict about a mesh that doesn't exist.

**Paint is a mode, not a takeover, and its engine is pure.** `studio/paint/` is a layered raster editor -- blend arithmetic, canvas-sized layers with stable uids, typed undo edits, 8-bit selection masks, a cached brush stamp, gradients, geometry, OpenRaster I/O -- and nothing under it may import imgui, moderngl, pygame or `service`, which is what makes every rule about pixels assertable headlessly. Three consequences are load-bearing. **Undo is dirty-rect patches addressed by layer uid**, never by index, so an undo issued after a reorder still lands on the layer the edit was made to; only whole-canvas geometry copies, and it redoes by *replaying* rather than storing a second copy. **Dirty is a comparison against `history.head`, not a flag** -- `Document.rev` counts changes and an undo is a change, so a rev-based check would call an undone document unsaved forever. And **the eraser cuts alpha**: the old `erase_color` became `Document.matte`, applied once at flatten, so what a photo exports onto is a property of the document rather than of every stroke. `studio/paint_mode.py` is the only layer that knows about jobs and task threads: no dialog and no encode ever runs on the frame thread, which is why saving is a state (`PaintDoc.saving`) rather than a call that returns, and why a failed save has to clear it (`on_task_failed`) or the tab stays read-only.

**A painted reference is a job row with no worker run.** `jobs.import_reference` mints a `done` reference from pixels the user drew -- `JobStore.create` takes an explicit status for exactly this, in one statement, because a create-then-claim pair leaves a window in which the worker's poll picks the job up and tries to run it. `assets/<job_id>/paint.ora` is the layered source behind a hand-edited reference, following the `input.orig.png` precedent: deliberately absent from `MEDIA`/`LISTED`, never served, and treated as **stale when it is older than `input.png`** -- a revert or a regenerate rewrites the reference without touching the layers, and resurrecting them would show an edit of an image that is gone. The flat half still goes through the untouched `files.save_edited_image`, so the original backup, `hand_edited`, the reference re-measure and the staged replace are all unchanged.

**One GL context, and imgui draws through moderngl.** `studio/imgui_backend.py` reimplements imgui's OpenGL3 backend on moderngl rather than using imgui-bundle's own, which draws through PyOpenGL: moderngl caches GL state, so raw `glBindTexture`/`glUseProgram` calls behind its back leave the viewport rendering with whatever the panels last bound. The same bridge is why `widgets.texture_ref` *registers* a texture as well as wrapping it — an id the renderer does not know maps to no moderngl object, and every image in the UI comes out as the font atlas.

**Rendering parity is against three r170's stock pipeline, not against an idea of PBR.** The browser build never wrote a custom shader, so `viewer/programs.py` reimplements what three does: the Stephen Hill ACES fit *with* its `/0.6` pre-scale (dropping it is the classic "everything is dark" bug), the exact piecewise sRGB OETF, and the Lazarov/Karis `DFGApprox` polynomial three itself uses. The viewport background is deliberately **not** tone-mapped -- three sets the clear colour straight back to sRGB, so it is the literal hex. `viewer/env.py`'s gradient probe exists for one reason: ambient from *below*, without which a quarter of every mesh renders darker than the background and reads as holes.

**The GLB loader is hand-rolled on purpose.** trimesh discards a scene root's transform -- which is exactly where `normalize_glb` puts the grounding transform -- and has no notion of a skin. `viewer/gltf.py` keeps the node graph live after loading, because posing is setting a joint node's local rotation and recomputing world matrices.

## Stack

- Python 3.12+, uv-managed (`uv sync --extra dev --extra studio`, `uv run pytest`, `uv run ruff check .`). No web framework: `httpx` remains only because `trellis-server.exe` speaks HTTP on a local port.
- `trellis-server.exe` is a vendored compiled binary (`vendor/`), not a Python package — confirm behavior against its actual CLI help / exposed routes, not against the upstream TRELLIS project's docs
- **An image model is a registry spec, not a directory.** `models.py` owns `BASE_MODELS` / `STYLE_LORAS`: a `BaseModel` carries its dir name *and* the settings it must run at (size, steps, guidance, variant, scheduler, always-on step-distillation LoRA), because those are properties of the checkpoint — a 4-step distilled model run at 25 steps with CFG produces mush, and Hyper-SD silently degrades without trailing timestep spacing. Add a model there, never by hardcoding constants in `pipelines/text2image.py`. `guidance.py` validates and stores the selection but deliberately keeps model keys and LoRA trigger words out of `_PROMPT_FIELDS` — triggers are prepended next to `PROMPT_TEMPLATE` instead.
- **One base model resident at a time.** The 32 GB card holds trellis (~16 GB) plus a single SDXL-class pipe (~7 GB) and not two, so `Worker._get_text2image(base_key)` unloads the previous pipe (via `asyncio.to_thread`) before building the next. Style LoRAs are the opposite: adapters on the resident pipe, switched per job with `set_adapters()` and no reload.
- SDXL-Turbo (`models/sdxl-turbo`) is the default because FLUX is gated — **both `dev` and `schnell`**, and 12B params won't coexist with trellis anyway. All weights are one-time manual `hf download`s under `WARLOCK_T2I_ROOT` (default `models/`); `WARLOCK_T2I_DIR` still relocates the `turbo` entry only. See `pipelines/text2image.py`
- **A skeleton is a JSON template, not code.** `src/warlock/templates/*.json` hold normalized landmark joints in a unit bbox (Blender axes: +X the subject's left, −Y forward, +Z up; x/y span −0.5..0.5, z spans 0..1). `rigging.fit_template` scales them onto the measured mesh bbox. Add a skeleton by adding a file, never by hardcoding bones in `blender_worker.py`. Fitting is bbox-proportional and deliberately approximate — the fitted positions are recorded in `rig.json` so a later "adjust joints" pass can correct them without re-rigging.
- Rigging is the `rig` extra (`uv sync --extra rig`). bpy ships **cp313 wheels only**, so the requirement carries a `python_version` marker — without it the whole project becomes unresolvable on 3.12 rather than just losing rigging. Missing bpy is non-fatal everywhere: `doctor.blender_check` reports it and the UI hides the rig controls.
- `docs/NEXT.md` is forward-planning only — a roadmap of things that are *not* built yet, not a description of the app

See memory (`warlock-stack.md`) for more background on this stack.
